### 1.1 数据模型（Data Model）

**新增内容：数据模型的三层划分**

**是什么**

Python 里"数据模型"这个词经常被含糊地等同于"随便一个存数据的类"，但工程上至少要拆成三层，因为它们的**信任边界不同、生命周期不同、该不该做运行时校验也不同**：

| 层级 | 典型工具 | 是否运行时校验 | 数据来源 |
|---|---|---|---|
| 定义数据结构 | `dataclass` | 否 | 程序内部自己构造 |
| 运行时数据流转 | `TypedDict` | 否（纯类型标注，运行时就是普通 dict） | 模块间传递，彼此信任 |
| 接口级数据流转 | `pydantic.BaseModel` | 是 | 外部输入（HTTP body、消息队列、第三方 API 返回） |

`dataclass` 解决的是"我懒得写 `__init__`"，本质是一个语法糖，`__eq__`、`__repr__` 都是自动生成的，但不会检查你传进来的字段类型是否正确。

`TypedDict` 解决的是"字典太灵活了，IDE 没法补全、类型检查器抓不到错"，它给 dict 的 key/value 打上类型标注，但运行时它就是个普通 dict，赋错类型也不会报错——检查完全靠 mypy 静态跑，程序真跑起来是没有任何防护的。这就是为什么它适合"内部高频、彼此信任"的场景：两个内部函数之间传一个配置字典，没必要每次都花运行时校验的开销。

`pydantic.BaseModel` 解决的是"外部数据不可信"这件事：一旦数据跨越了信任边界（前端传来的 JSON、别的微服务返回的 payload），就必须在运行时真正校验类型、格式、约束，校验失败要能抛出结构化的错误信息。这是它和前两者最本质的区别——**它是运行时防线，不只是类型标注**。

**为什么要谈这个**

大部分人对这三个工具的选择是"哪个用着顺手用哪个"，结果常见两种事故：一是在内部高频调用路径上无脑上 `BaseModel`，校验开销拖慢了本该很快的内部函数；二是在处理外部输入时图省事用了 `TypedDict` 或 `dataclass`，脏数据（类型错误、字段缺失、恶意构造的超长字符串）直接穿透到业务逻辑甚至数据库层，出了问题还很难定位是哪个环节漏了校验。工程能力和脚本能力的分野，很大程度上就体现在"你是不是清楚每一份数据现在处在信任链的哪个位置"。

* `id()`、`is`、`==`

### 1.4 Pythonic

**新增内容：泛型化 Schema 设计与 ORM 映射初始化参数**

**是什么**

**(a) 泛型化的 Response 设计**

不用泛型时，一个典型的后端项目会为每个资源重复写一遍几乎一样的响应结构（`UserResponseSchema`、`OrderResponseSchema`……），唯一变化的只是内部装的数据类型。用 `Generic[T]` 改写后，可以定义一个通用的 `ResponseSchema[T]`，用 `data: T` 承载任意资源类型，使用时以 `ResponseSchema[list[UserSchema]]`、`ResponseSchema[list[OrderSchema]]` 的方式实例化。再进一步，分页场景可以单独抽出 `PaginatedResponse[T]`，包含 `total`、`page`、`page_size`、`items: list[T]` 这类通用字段，所有资源的分页接口复用同一套结构，而不是每个资源都手写一遍分页壳子。这就是"用一个 `ItemSchema` 泛型，进而表达出所有 `xxResourceResponseSchema`"背后真正省下来的重复劳动。

**(b) ORM 映射初始化时的 `exclude_unset` / `exclude_none`**

当 pydantic 模型要从 ORM 对象（比如 SQLAlchemy 的 model 实例）转换过来时，通常用 `model_validate(orm_obj, from_attributes=True)`，这条链路本身没什么陷阱。真正容易踩坑的是**反向操作**——用一个 pydantic 模型去局部更新（PATCH）一个已存在的数据库对象时：

* `exclude_unset=True`：只导出客户端**明确传了**的字段。这在 PATCH 场景是必须的——如果不加这个参数，客户端只想改一个字段，但其他没传的字段会被 pydantic 用默认值填上，一旦原样 `update()` 回数据库，其他字段就会被误清空。
* `exclude_none=True`：导出时排除值为 `None` 的字段，常用在序列化输出、不想把空字段吐给前端的场景，但和 `exclude_unset` 解决的是完全不同的问题——一个关心"有没有传"，一个关心"值是不是 None"，两者不能混用误解。

**为什么要谈这个**

如果没有泛型化的通用 Schema 设计，项目里资源一多，重复代码会指数级增长，可维护性直接崩掉——这是"能跑"和"工程化"之间很典型的分界线。而 `exclude_unset`/`exclude_none` 看着只是两个不起眼的参数，实际上是 PATCH 类接口正确性的核心：用错的话，最常见的线上事故就是"用户只改了一个字段，结果其他字段全被 None 覆盖清空了"——这种 bug 往往上线很久才被发现，因为大部分测试只测"传了所有字段"的正常路径，恰恰漏了"只传部分字段"这个真实用户行为。

插件系统（Plugin System）

**新增内容：插件系统即六边形架构的落地**

**是什么**

插件系统这个练习题，实质上就是在具体实现**六边形架构（Hexagonal Architecture，也叫 Ports & Adapters 模式）**：核心思想是把"业务要做什么"（Port，接口）和"具体怎么做"（Adapter，实现）彻底解耦，让核心逻辑不依赖任何具体实现细节。

用"文档抽取器"这个例子最容易讲清楚：

* **Port（统一接口）**：主程序对外只暴露一个统一的 `read(file) -> Document` 接口，调用方完全不需要知道文件到底是什么格式。
* **Adapter（具体实现）**：`PDFAdapter`、`DocxAdapter`、`ExcelAdapter` 等分别实现"怎么读某一种具体格式"的细节，它们都遵守同一个抽象基类/协议约定，可以被动态注册、动态加载、按文件类型自动路由。
* **资源管控归主程序**：无论底层加载了哪个 Adapter，文件句柄的打开关闭、并发数量限制、超时控制、异常兜底，这些"资源生命周期"层面的事情，统一由主程序管理，Adapter 只管"怎么解析"，不该、也不能碰资源管理这一层。这个边界划分本身就是六边形架构里"核心不依赖细节"的体现——哪天要新增一种文件格式的 Adapter，主程序的资源管控逻辑完全不用动。

**为什么要这么设计着讲，而不是停留在"抽象基类+多态"**

如果只讲"定义一个 ABC，几个子类重写方法，多态调用"，这是语法层面的东西，学完很容易忘了这套语法到底解决了什么真实工程问题。用六边形架构 + 具体的文档抽取器场景来讲，是想让这个知识点落到"如何设计一个可扩展、职责边界清晰的中大型模块"这个真正的工程决策能力上。而且这套 Port/Adapter 的思路在后端开发里几乎无处不在——存储后端可以换（本地磁盘/S3/OSS）、消息队列可以换（Kafka/RabbitMQ）、认证方式可以换（JWT/OAuth/Session），提前把这个模式吃透，对接下来学 Backend Engineering 是直接可复用的底层认知，而不是孤立的语法练习。

## 必做项目

**新增内容：打通 Context Manager、Generator 与手写事件循环**

**是什么**

这一段要把三件表面上不相关、底层却共享同一个机制的东西串起来讲，机制就是：**函数执行到一半可以暂停，把控制权交出去，之后再被恢复执行**——这正是 `yield` 的本质。

**(a) `@contextmanager` 里的 `yield` vs 生成器里的 `yield`**

`@contextmanager` 里的 `yield` 只会被执行一次，语义是"暂停在这里，把资源交给 with 块内的代码用；等 with 块结束，回来继续执行 yield 后面的收尾代码"——本质是把 `__enter__`/`__exit__` 这两段代码通过一次 yield 缝合成一个函数。

而普通生成器里的 `yield` 可以出现在循环里、被反复触发多次，每次调用 `next()` 才会往下走一步，这是"惰性地、一步步吐出数据"的语义，用来做数据流水线、无限流处理。

两者用的是同一个关键字、同一套底层机制（生成器对象、`send()`/`throw()`/`close()` 协议），但语义上一个是"资源的进入退出"，一个是"数据的持续产出"——不把这层底层共性讲清楚，学的人很容易觉得这是两个不相关的知识点各自死记。

**(b) 手写一个最简单的事件循环**

不依赖真正的 `asyncio` 库，自己实现一个 mini 版本：一个任务队列 + 一个循环，协程执行到 `await` 就相当于 `yield` 出控制权，事件循环拿到控制权后去推进下一个协程，这样单线程内就实现了"看起来并发"的调度。这样做的目的是把 `asyncio`、`create_task`、`gather` 这些 API 背后的黑盒打开——很多人用了很久 asyncio，但从来没有真正理解过"为什么它是单线程却能并发"、"为什么 CPU 密集型任务放到 asyncio 里没有任何加速效果"。手写一遍之后，这些问题自然就有答案了。

**(c) 顺带讲清楚线程安全**

因为 asyncio 的事件循环本质是单线程、协作式调度（同一时刻只有一个协程在真正执行代码，不会被随时打断），所以在纯 asyncio 内部，普通的共享变量不需要加锁——这和多线程编程里"随时可能被打断，必须加锁"的直觉完全相反，很多人是带着多线程的恐惧来学 asyncio 的，反而多此一举地到处加锁。但一旦涉及到 asyncio 和真正的多线程混用（比如用 `run_in_executor` 跑阻塞的同步代码、或者从另一个线程往事件循环里塞任务），线程安全问题就重新出现了，这时候需要用 `call_soon_threadsafe` 这类专门的跨线程安全接口，不能像 asyncio 内部那样随意共享状态。

**为什么要这样打通着讲**

这三块内容如果分开孤立地学（Context Manager 一节课、Generator 一节课、asyncio 一节课），学完往往还是不明白"为什么它们都用 `yield`，行为却完全不同"，也不明白 asyncio 的并发本质到底是什么——很多人能背出 `async/await` 的语法，却说不出事件循环内部在干什么。手写一遍 mini event loop，能把"协程调度"从一个只会调 API 的黑盒，变成真正理解其原理的白盒，这才是这块知识真正掌握与否的分水岭；顺带把线程安全的认知也一起纠正过来，避免"异步 = 多线程"这种很常见但完全错误的初学者直觉，为后面做高并发系统设计打好底层认知基础。
