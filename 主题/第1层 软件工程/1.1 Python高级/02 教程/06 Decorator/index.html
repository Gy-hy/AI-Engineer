    Decorator（★★★★★）¶

    目标：理解 Python 装饰器的完整机制——它只是高阶函数的语法糖，但 functools.wraps、参数装饰器、多层装饰器的应用顺序，是区分"会用"和"真懂"的分水岭。

    一、装饰器是什么：高阶函数的语法糖¶

    1.1 本质：接受函数、返回函数¶

    在 Python 里，函数是一等公民：可以赋值给变量、作为参数传递、作为返回值返回。装饰器的全部秘密，就是这一条性质的直接应用——装饰器是一个"接受函数、返回新函数"的函数：

    def deco(func):          # 接受一个函数
    def wrapper(*args, **kwargs):
        print("调用前")
        result = func(*args, **kwargs)
        print("调用后")
        return result
    return wrapper       # 返回一个新函数

    wrapper 里捕获了 func，这就是闭包（closure）——内层函数记住了外层函数的局部变量。装饰器能工作的底层机制就是闭包。

    1.2 @ 是语法糖¶

    @deco
def target():
    return 42

    完全等价于：

    def target():
    return 42
target = deco(target)   # 用 deco 的返回值替换原来的 target

    @deco 这一行，本质就是"定义完函数后，立刻把函数交给 deco，再用 deco 的返回值替换掉 target 这个名字"。理解了这一点，装饰器的所有行为都能推导出来。

    1.3 陷阱：装饰器在"定义时"执行，不是"调用时"¶

    这是装饰器第一个、也是最容易被忽略的认知点。@deco 这一行在模块被导入、函数被定义的那一刻就执行了，而不是等到 target() 被调用时：

    def deco(func):
    print(f"deco 正在包装 {func.__name__}（定义时执行）")
    def wrapper(*a, **k):
        return func(*a, **k)
    return wrapper

@deco
def f():
    pass
# 上面这行定义完，deco 就已经执行了，立刻打印"deco 正在包装 f"

f()   # 这行只执行 wrapper，不再执行 deco
f()   # 每次调用执行的都是 wrapper

    实测：deco 只在定义时执行一次；之后每次 f() 执行的都是 wrapper。这个区分的工程含义是——装饰器的"重活"（注册、验证、准备）应该放在 deco 层做一次；"轻活"（每次调用都要做的）才放在 wrapper 层。把每调用一次都要重复的昂贵操作误写进 deco 层，会导致"只执行一次"变成"每次执行"，或反过来。

    二、函数装饰器¶

    2.1 基础形式¶

    def timer(func):
    import time
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} 耗时 {elapsed:.4f}s")
        return result
    return wrapper

@timer
def slow():
    import time
    time.sleep(0.01)

slow()   # slow 耗时 0.0100s

    wrapper 用 *args, **kwargs 原样透传参数、返回原函数的返回值，保证装饰后的函数"签名行为"和原来一致。

    2.2 functools.wraps：为什么必须¶

    上面的 timer 有一个隐患：slow.__name__ 已经变成 "wrapper" 了，slow.__doc__ 也丢了。实测：

    def no_wraps(func):
    def wrapper(*a, **k):
        """wrapper 自己的 docstring"""
        return func(*a, **k)
    return wrapper

@no_wraps
def original():
    """original 的 docstring"""
    return 42

original.__name__   # 'wrapper'  ← 元信息被覆盖了
original.__doc__    # 'wrapper 自己的 docstring'

    元信息丢失会带来连锁问题：日志里函数名全变成 wrapper、文档工具拿不到 docstring、一些框架靠 __name__ 做路由（如 Flask 的视图函数）会直接出错。修复方式是在 wrapper 上套一层 @functools.wraps(func)：

    import functools

def with_wraps(func):
    @functools.wraps(func)
    def wrapper(*a, **k):
        return func(*a, **k)
    return wrapper

@with_wraps
def original2():
    """original2 的 docstring"""
    return 42

original2.__name__    # 'original2'  ← 保留
original2.__doc__     # 'original2 的 docstring'
original2.__wrapped__ # 指向原始函数，可被 inspect 递归展开

    functools.wraps 内部调用的是 functools.update_wrapper，它把原函数的 __name__、__doc__、__dict__（自定义属性）等拷贝到 wrapper 上，并设置 __wrapped__ 指向原函数。

    铁律：凡写装饰器，wrapper 上必套 @functools.wraps(func)，除非你有明确理由不这么做。

    三、参数装饰器¶

    3.1 三层嵌套结构¶

    @deco 这种不带参数的装饰器是两层（deco 返回 wrapper）。但很多时候我们想让装饰器"可配置"——比如 @retry(times=3)、@rate_limit(per_minute=60)。带参数的装饰器是三层嵌套：

    def repeat(times):           # 第 1 层：接收装饰器参数，返回"真正的装饰器"
    def deco(func):          # 第 2 层：接收被装饰函数，返回 wrapper
        @functools.wraps(func)
        def wrapper(*a, **k):   # 第 3 层：实际替换原函数的函数
            return [func(*a, **k) for _ in range(times)]
        return wrapper
    return deco

@repeat(3)
def hi():
    return "hi"

hi()   # ['hi', 'hi', 'hi']

    理解三层结构的关键：@repeat(3) 等价于 hi = repeat(3)(hi)。repeat(3) 先执行，返回 deco；deco(hi) 再执行，返回 wrapper。所以"参数装饰器"本质就是"一个返回装饰器的函数"，并没有任何新机制，只是多套了一层。

    3.2 心智模型：参数装饰器 = 无参装饰器的"工厂"¶

    把上面拆开看最清楚：

    deco = repeat(3)     # 先"配置"出一个无参装饰器
@deco                # 再用它装饰，等价于 hi = deco(hi)
def hi():
    return "hi"

    一层一层拆，就回到了 1.2 节的语法糖。凡是看到 @xxx(args)，先问自己：xxx(args) 返回的是什么？——返回的一定是个装饰器。

    四、多层装饰器¶

    4.1 应用顺序：从下往上¶

    多个装饰器叠加时，最靠近函数的那一个先应用：

    def a(func):
    def w(*x, **k): return "A(" + func(*x, **k) + ")"
    return w

def b(func):
    def w(*x, **k): return "B(" + func(*x, **k) + ")"
    return w

@a
@b
def core():
    return "core"

core()   # 'A(B(core))'

    拆开看就是 core = a(b(core))：先 b 包住 core，再 a 包住 b 的结果。调用时由外向内（先执行 a 的 wrapper，再 b 的 wrapper，最后 core）；应用时由内向外（先应用 b，再应用 a）。记住一句："越靠近函数的，越先被应用、越晚被执行"。

    五、类装饰器¶

    装饰器的参数不一定是函数，也可以是类。类装饰器就是"接受类、返回类"的函数，常用于给类统一加属性、方法、注册到某个注册表：

    def add_greeting(cls):
    cls.greet = lambda self: f"Hello, I'm {cls.__name__}"
    return cls

@add_greeting
class Person:
    pass

Person().greet()   # "Hello, I'm Person"

    类装饰器的典型应用是依赖注入容器（@injectable）、ORM 模型注册（把类登记到全局模型表）、单例模式（见第七节）。它的执行时机和函数装饰器一样，也是"类定义完成时"执行。

    六、应用：五个实战装饰器¶

    装饰器的价值在"横切关注点"（cross-cutting concerns）：日志、重试、缓存、鉴权、计时这些逻辑，和业务逻辑无关，却会散落在每个函数里。用装饰器能把它们抽出来，一处定义、处处复用。下面五个是后端工程里最高频的：

    import functools, time

def timer(func):
    """计时：打印函数耗时。"""
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} 耗时 {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

def retry(times=3, delay=0):
    """重试：异常时退避重试。"""
    def deco(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except Exception:
                    if attempt == times - 1:
                        raise
                    time.sleep(delay)
        return wrapper
    return deco

def cache(func):
    """缓存：用入参做键，缓存返回值（适合纯函数）。"""
    memo = {}
    @functools.wraps(func)
    def wrapper(*args):
        if args not in memo:
            memo[args] = func(*args)
        return memo[args]
    return wrapper

def authorize(required=True):
    """鉴权：调用前检查权限。"""
    def deco(func):
        @functools.wraps(func)
        def wrapper(user, *args, **kwargs):
            if required and not getattr(user, "is_admin", False):
                raise PermissionError("无权限")
            return func(user, *args, **kwargs)
        return wrapper
    return deco

def singleton(cls):
    """单例：类装饰器，保证一个类只实例化一次。"""
    instances = {}
    @functools.wraps(cls)
    def get_instance(*args, **kwargs):
        if cls not in instances:
            instances[cls] = cls(*args, **kwargs)
        return instances[cls]
    return get_instance

    注意这五个里 timer 是无参装饰器（两层），retry/authorize 是参数装饰器（三层），singleton 是类装饰器——恰好覆盖了本章全部三种形态。

    七、必做项目：Decorator Library¶

    完整示例代码项目待补（示例代码/decorator_lib/），本节先给接口设计与核心实现，可直接内联验证。

    7.1 需求¶

    实现一个装饰器库，包含五个装饰器：retry、timer、cache、singleton、authorize。要求每个都支持合理配置、都用 functools.wraps 保留元信息、都能独立使用也能叠加使用。

    7.2 接口设计¶

    装饰器 形态 签名 关键行为
    timer 无参 @timer 打印耗时，返回原结果
    retry 有参 @retry(times=3, delay=0) 异常退避重试，耗尽后抛出
    cache 无参 @cache 按入参缓存，仅适用纯函数
    singleton 类装饰器 @singleton 类只实例化一次
    authorize 有参 @authorize(required=True) 调用前鉴权，失败抛 PermissionError

    核心实现即第六节的五个函数。一个可验证的叠加示例：

    @timer
@retry(times=3, delay=0.1)
@cache
def fetch(k):
    # 模拟可能失败的调用
    return k * 2

# timer 包着 retry 包着 cache：
# 调用时先计时，再重试，最后命中/写入缓存

    7.3 验收标准（毕业标准）¶

    1. 元信息不丢：fetch.__name__ 仍是 "fetch"，fetch.__doc__ 保留（每个装饰器都用了 wraps）。
    2. retry 生效：故意让函数前两次抛异常、第三次成功，观察它能重试到成功；让函数永远失败，观察它耗尽后把异常抛出来。
    3. cache 生效：给函数加计数器，多次调用相同入参，观察函数体只执行一次。
    4. singleton 生效：两次实例化，is 判断为同一对象。
    5. 叠加顺序正确：@timer + @retry + @cache 叠加时，打印的耗时是"含重试的整段耗时"，符合"由外向内"的执行顺序。

    八、全章速查表¶

    知识点 一句话要点
    装饰器本质 接受函数、返回函数的函数——高阶函数的语法糖
    @deco 等价于 func = deco(func)
    底层机制 闭包：wrapper 捕获外层 func
    执行时机 装饰器在定义时执行一次，wrapper 每次调用执行
    functools.wraps 保留 __name__/__doc__/__dict__，设 __wrapped__
    参数装饰器 三层嵌套——"返回装饰器的函数"
    多层装饰器 从下往上应用；调用时由外向内
    类装饰器 接受类、返回类，用于统一加属性/注册
    无参装饰器 两层（deco → wrapper）
    有参装饰器 三层（工厂 → deco → wrapper）
    典型应用 timer / retry / cache / authorize / singleton
    横切关注点 与业务无关、散落各处的逻辑，用装饰器一处定义处处复用

    九、贯穿全章的一条判断¶

    最后收束到这一章要建立的认知：

    装饰器不引入任何新语法机制——它只是"函数是一等公民 + 闭包"的语法糖。真正需要理解的是执行时机和应用顺序。

    • 想要一处定义、处处复用的横切逻辑（日志/重试/缓存/鉴权）→ 用装饰器抽出来，别在每个函数里复制粘贴。
    • 想要装饰后的函数仍然"像自己"（能被日志、路由、文档工具正确识别）→ 每个 wrapper 都套 @functools.wraps。
    • 想要可配置的装饰器 → 多套一层变成三层，本质是"返回装饰器的函数"。

    理解装饰器的标志，不是会写 @xxx，而是能说清楚：@a @b 谁先应用、谁先执行，@retry(3) 的三层各自在什么时候跑，functools.wraps 到底保住了什么。这三点通了，后面读 FastAPI 的 @app.get()、pytest 的 @fixture、Flask 的 @route 这些框架装饰器，就都是同一套东西的变体。
