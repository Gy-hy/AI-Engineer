    Packaging（★★★★★）¶

    目标：理解现代 Python 项目的打包规范——pyproject.toml 的三大配置表、src 布局为什么能避免 import 陷阱，以及用 uv 完成"构建 → 发布"的完整流程。

    一、为什么需要打包¶

    1.1 脚本 vs 包¶

    写一个 .py 脚本自己跑，和写一个能被别人 pip install 的包，是两种完全不同的工程形态。前者靠 sys.path 碰运气，后者有明确的元数据（名字、版本、依赖、Python 版本要求）、明确的入口、明确的安装方式。

    1.2 打包解决的三件事¶

    1. 可安装——pip install / uv add 一条命令装好，不用手动拷贝文件。
    2. 可声明依赖——依赖写在 pyproject.toml 里，别人安装时自动拉取、锁定版本。
    3. 可发布——构建成 .whl/.tar.gz，上传到 PyPI（或公司私有源），全团队复用。

    二、pyproject.toml：现代项目的心脏¶

    pyproject.toml 是 PEP 518 引入的"项目元数据单文件"，取代了旧时代的 setup.py + setup.cfg + requirements.txt 三件套。一个包的所有信息都在这里。

    2.1 三个关键表¶

    [build-system]                       # 表 1：怎么构建这个包
requires = ["hatchling"]             #   构建后端（build backend）
build-backend = "hatchling.build"

[project]                            # 表 2：包是什么
name = "mypkg"
version = "0.1.0"
description = "最小打包演示"
requires-python = ">=3.12"           #   声明 Python 版本要求
dependencies = []                    #   运行依赖

[project.optional-dependencies]      # 可选依赖（extra）
dev = ["pytest>=8.0"]
    • [build-system]：用哪个构建后端。现代主流是 hatchling（uv 默认）、setuptools（最老牌）、flit-core、poetry-core。构建后端负责把源码打成 wheel。
    • [project]：包的核心元数据——名字、版本、描述、依赖、Python 版本。
    • [tool.xxx]：各工具的配置（如 [tool.pytest.ini_options]、[tool.ruff]），格式由工具自己定义。

    2.2 最小可构建配置¶

    一个能 uv build 出 wheel 的最小项目（已实测构建成功）：

    mypkg/
├── pyproject.toml
└── src/
    └── mypkg/
        └── __init__.py

    # pyproject.toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "mypkg"
version = "0.1.0"
description = "最小打包演示"
requires-python = ">=3.12"
dependencies = []

    # src/mypkg/__init__.py
__version__ = "0.1.0"
def hello():
    return "hello from mypkg"

    2.3 依赖锁定¶

    dependencies 里写的是"依赖谁、允许什么版本范围"（如 httpx>=0.27）。但范围是宽松的，要保证"每个人装出来都一样"，需要锁定文件——uv 生成 uv.lock，poetry 生成 poetry.lock。锁定文件记录了解析出的确切版本，应提交进 git，保证环境可复现。

    三、src 布局¶

    3.1 为什么用 src/¶

    推荐结构是"src 布局"——代码放在 src/ 目录下，而不是项目根目录：

    项目根/
├── pyproject.toml
├── src/
│   └── mypkg/
│       ├── __init__.py
│       └── core.py
└── tests/
    └── test_core.py

    src 布局的核心好处是避免一个隐蔽的 import 陷阱：如果把包放在根目录，你"直接在当前目录跑 python"时，会意外 import 到本地源码目录而不是已安装的包，导致"测试跑的是没安装的代码、装完才发现不一样"。src 布局强制你必须先"安装"才能 import（因为源码不在根目录、sys.path 里没有它），从而保证你测试的代码 == 用户安装的代码。这是 PyPA 官方推荐、绝大多数现代项目采用的布局。

    3.2 配套配置¶

    用 setuptools 做后端时，需要显式告诉它包在 src/ 下（collection_lib 的真实配置）：

    [tool.setuptools.packages.find]
where = ["src"]

    用 hatchling 则默认就能识别 src/ 布局，无需额外配置——这也是 hatchling 渐成主流的便利之处。

    四、构建与发布¶

    4.1 uv build¶

    uv build
# Building source distribution...
# Building wheel from source distribution...
# Successfully built dist/mypkg-0.1.0.tar.gz
# Successfully built dist/mypkg-0.1.0-py3-none-any.whl

    uv build 会产出两个产物到 dist/：

    • .whl（wheel）：预编译的二进制发行版，pip install xxx.whl 直接装，是安装的主要形态。
    • .tar.gz（sdist，source distribution）：源码包，供从源码构建（如没有对应 wheel 的平台）。

    4.2 本地安装测试¶

    发布前先在本地验证"装出来能不能用"：

    # 方式一：uv 添加本地包（开发模式，改代码即时生效）
uv pip install -e .

# 方式二：从构建产物安装（模拟真实用户）
uv pip install dist/mypkg-0.1.0-py3-none-any.whl

    -e（editable，可编辑模式）安装的是"链接"而非拷贝，改源码立即生效，适合开发期；从 wheel 安装则是"真实用户"的安装方式，发布前务必验证一次。

    4.3 发布到 TestPyPI / PyPI¶

    # 先发布到 TestPyPI（练习用，不影响真实用户）
uv publish --publish-url https://test.pypi.org/legacy/ --token $TEST_PYPI_TOKEN

# 验证无误后再发正式 PyPI
uv publish --token $PYPI_TOKEN

    发布需要先到 PyPI 官网申请一个 API token，并把它放进环境变量（不要硬编码进代码或提交 git）。TestPyPI 是练习发布的"沙盒"，正式发 PyPI 前先在上面走通全流程，是工程上的好习惯。

    五、工具链：uv / pip / poetry¶

    5.1 uv vs pip¶

    维度 pip uv
    定位 老牌标准 新一代，Rust 重写
    速度 较慢 快一个数量级（并行解析 + 缓存）
    锁定 无原生锁文件 uv.lock 精确锁定
    命令 pip install/build uv add/remove/sync/build/publish

    uv 不是"另一个 pip"，而是"pip + venv + pip-tools + build + twine"的一体化替代。它兼容 pyproject.toml 和 PyPI 生态，可以逐步替换，不用一次切换。本项目 README 里已采用 uv 作为推荐工具。

    5.2 poetry（了解）¶

    poetry 是另一套流行的依赖管理工具（pyproject.toml 的早期推动者之一），提供 poetry add/install/build/publish 及 poetry.lock。它和 uv 解决的是同一类问题。现代新项目选 uv 的越来越多（速度优势明显），但老项目里 poetry 仍广泛存在，见到能看懂即可。

    六、必做项目：发布自己的 Python Package¶

    完整示例代码项目待补（示例代码/ 下已有 collection_lib、plugin_system 两个现成可发布的包，可直接复用它们练手）。

    6.1 需求¶

    把之前做的某个项目（如 collection_lib 或 plugin_system）打包，发布到 TestPyPI（可选：正式 PyPI）。

    6.2 步骤¶

    1. 确认 pyproject.toml 完整：name、version、requires-python、dependencies 齐全。
    2. 采用 src 布局，代码在 src/ 下。
    3. 本地 uv build，确认 dist/ 里产出 wheel + sdist。
    4. uv pip install dist/*.whl 到干净环境，验证 import 与核心功能可用。
    5. 到 TestPyPI 申请 token，uv publish --publish-url https://test.pypi.org/legacy/ --token ... 发布。
    6. 从 TestPyPI 装回来验证：uv pip install --index-url https://test.pypi.org/simple/ 你的包名。

    6.3 验收标准（毕业标准）¶

    1. 可构建：uv build 无错误产出 wheel 和 sdist。
    2. 可安装：干净环境里 pip install wheel 后，能正常 import 并调用。
    3. 可发布：包成功出现在 TestPyPI 上，且能从 TestPyPI 重新安装。
    4. 元数据正确：requires-python、dependencies 声明与实际一致，安装时依赖被正确拉取。
    5. src 布局：代码在 src/ 下，测试的是"已安装的代码"而非"本地源码"。

    七、全章速查表¶

    知识点 一句话要点
    pyproject.toml 项目元数据单文件，取代 setup.py 三件套
    [build-system] 声明构建后端（hatchling / setuptools / poetry-core）
    [project] 包名、版本、依赖、requires-python
    [tool.xxx] 各工具的配置区
    依赖锁定 uv.lock / poetry.lock 记录精确版本，保证可复现
    src 布局 代码放 src/，强制"先安装再 import"，测试代码 == 用户装到的代码
    uv build 产出 wheel（.whl）+ sdist（.tar.gz）到 dist/
    -e 可编辑安装 开发期链接安装，改码即时生效
    uv publish 发布到 PyPI/TestPyPI，需 API token
    TestPyPI 发布练习的沙盒，正式发布前先走通
    uv vs pip uv 更快、带锁文件，是 pip+venv+build+twine 一体化

    八、贯穿全章的一条判断¶

    最后收束到这一章要建立的认知：

    打包不是"把代码打个 zip"，而是"给代码建立可安装、可声明依赖、可复现的工程边界"。

    • 想要别人一条命令装好你的代码 → 写全 pyproject.toml，uv build 出 wheel。
    • 想要测试的代码 == 用户装到的代码 → 用 src 布局，避免 import 到本地源码的陷阱。
    • 想要环境可复现 → 用锁文件（uv.lock）钉死精确版本。

    理解打包的标志，不是会敲 pip install，而是能说清楚：[build-system] 和 [project] 各管什么、src 布局到底防了什么坑、wheel 和 sdist 的区别。这三点通了，"从写一个能跑的脚本"到"维护一个能发布、能协作的包"，就跨过了那条工程化的分界线。
