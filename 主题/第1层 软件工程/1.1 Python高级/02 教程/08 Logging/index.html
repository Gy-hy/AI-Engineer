    Logging（★★★★★）¶

    目标：理解 Python 标准库 logging 的完整机制——Logger/Handler/Formatter/Filter 四大组件如何协作，propagate 和"两道闸"这两个最易踩的坑，以及如何落地 Trace ID + JSON 日志的企业级规范。

    一、为什么需要结构化日志¶

    1.1 print 的三大局限¶

    新手调试爱用 print，但 print 一旦进入生产就暴露三个致命缺陷：

    1. 没有级别——print("调试信息") 和 print("严重错误") 长得一样，上线后你既分不清轻重，也没法"只保留错误、忽略调试"。
    2. 没有上下文——不知道这条输出来自哪个模块、哪个函数、什么时间、什么请求。
    3. 没有出口控制——print 只能打到标准输出，没法同时写文件、滚动、发到日志平台。

    logging 模块解决的就是这三件事：分级、带上下文、可路由到多个出口。

    1.2 日志的四个维度¶

    一条合格的日志，至少要回答四个问题：什么时候（时间戳）、谁（logger 名）、多严重（级别）、发生了什么（消息）。生产级日志还会加上哪个请求（Trace ID / Request ID），把同一次请求散落在各处的日志串起来。

    二、logging 的核心概念¶

    2.1 五个级别¶

    级别 数值 用途
    DEBUG 10 调试细节，生产默认关闭
    INFO 20 正常流程关键节点
    WARNING 30 可能有问题，但不影响运行
    ERROR 40 出错了，需要关注
    CRITICAL 50 致命错误，程序可能无法继续

    级别是过滤阈值：设成 INFO（20），就只输出 INFO 及更严重的（20~50），DEBUG 被过滤掉。

    2.2 四大组件¶

    组件 职责
    Logger 入口，应用程序代码通过它发日志
    Handler 出口，决定日志写到哪里（控制台/文件/网络）
    Formatter 决定日志长什么样（格式）
    Filter 更细粒度的过滤（按名字、按内容）

    一条日志的数据流是：Logger 产生 → Handler 路由 → Formatter 格式化 → 输出。Logger 可以有多个 Handler（同一条日志同时到控制台和文件），每个 Handler 有自己的 Formatter 和级别。

    2.3 最小可用示例¶

    import logging

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
logging.info("服务启动")
# 2026-10-11 23:55:30,123 INFO 服务启动

    basicConfig 是给 root logger 做一次性快速配置的入口，适合脚本；真正的工程项目会显式配置 Handler/Formatter。

    三、Logger¶

    3.1 getLogger(__name__) 命名习惯¶

    import logging
logger = logging.getLogger(__name__)   # 每个模块一个 logger，名字 = 模块路径

    用 __name__ 作为 logger 名，日志里就能看到"这条日志来自哪个模块"（如 app.service.user）。这是全 Python 社区的事实标准。

    3.2 点号层级与 propagate¶

    logger 名里的点号表示层级：app.module 的父 logger 是 app，app 的父是 root（实测确认）。子 logger 的日志默认会向上传播（propagate）到父 logger——这就是"子 logger 没配 handler，日志也能输出"的原因（消息一路传到 root 的 handler）。

    3.3 陷阱：propagate 默认 True 导致重复输出¶

    这是 logging 里最经典的坑。如果你给子 logger 配了 handler，却忘了关 propagate，子 logger 的日志会输出两次——一次是子 logger 自己的 handler，一次是传播到 root 再由 root 的 handler 输出：

    child = logging.getLogger("app.child")
child.addHandler(logging.StreamHandler())   # 子 logger 自己的 handler
# 此时 child.propagate 仍是 True（默认）

child.info("这条会打两次")
# 一次：child 自己的 handler
# 一次：传播到 root，root 的 handler 再打一次

    修复：给会自配 handler 的 logger 设 propagate = False，避免消息继续往上冒：

    child.propagate = False

    3.4 陷阱：logger 级别和 handler 级别是"两道闸"¶

    日志要能输出，必须同时通过两道过滤：

    1. logger 自己的级别（logger.setLevel(...)）
    2. handler 的级别（handler.setLevel(...)）

    实测：logger 设 DEBUG、handler 设 WARNING 时，info 过得了 logger 这道闸、过不了 handler 这道闸，最终不输出。很多人只调了 logger.setLevel，发现还是没输出，就是因为忘了 handler 也有一道闸（而且默认 handler 级别是 NOTSET，实际会继承 logger 的级别）。

    四、Handler¶

    4.1 StreamHandler / FileHandler¶

    import logging

logger = logging.getLogger("app")
logger.setLevel(logging.INFO)

# 控制台
console = logging.StreamHandler()
# 文件
file = logging.FileHandler("app.log", encoding="utf-8")

logger.addHandler(console)
logger.addHandler(file)

    一个 logger 挂多个 handler，同一条日志同时进控制台和文件——这就是"出口控制"。

    4.2 RotatingFileHandler：按大小滚动¶

    生产日志会无限增长，必须滚动切割。RotatingFileHandler 按文件大小滚动：

    import logging.handlers   # 注意：handlers 子模块要显式导入

handler = logging.handlers.RotatingFileHandler(
    "app.log", maxBytes=10_000_000,  # 10MB 滚动一次
    backupCount=5,                    # 保留 5 个旧文件 app.log.1 ~ app.log.5
    encoding="utf-8",
)

    实测：超过 maxBytes 会自动把当前文件改名为 app.log.1、旧的往后顺延，超过 backupCount 的最旧文件被删除。

    4.3 陷阱：logging.handlers 必须显式导入¶

    import logging 不会自动导入 handlers 子模块。直接写 logging.handlers.RotatingFileHandler 会报错：

    AttributeError: module 'logging' has no attribute 'handlers'

    必须显式 import logging.handlers（或 from logging.handlers import RotatingFileHandler）才能用。这是新手几乎必踩一次的坑。

    五、Formatter 与 Filter¶

    5.1 格式字符串¶

    formatter = logging.Formatter(
    "%(asctime)s %(levelname)s %(name)s: %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
)
handler.setFormatter(formatter)

    常用占位符：%(asctime)s（时间）、%(levelname)s（级别）、%(name)s（logger 名）、%(message)s（消息）、%(filename)s:%(lineno)d（代码位置）、%(funcName)s（函数名）。

    5.2 Filter¶

    Filter 用于比"级别"更细的过滤，比如"只放行某个名字的 logger"：

    class BlockDebug(logging.Filter):
    def filter(self, record):
        return record.name != "noisy.module"   # 屏蔽这个模块的所有日志

handler.addFilter(BlockDebug())

    filter 返回 True 放行、False 丢弃。它还能修改 record、给日志附加字段，是注入 Trace ID 的一种方式。

    六、工程实践：Trace ID / Request ID / JSON Log¶

    6.1 为什么需要¶

    生产环境一次用户请求会横跨多个服务、多个模块，各打各的日志。没有 Trace ID，你根本无法把散落的上百条日志按"同一次请求"串起来排查问题。JSON 日志则让日志可被日志平台（ELK、Loki 等）直接解析、索引、检索。

    6.2 实现：JSON Formatter + 上下文注入¶

    import json
import logging

class JsonFormatter(logging.Formatter):
    def format(self, record):
        data = {
            "time": self.formatTime(record, "%Y-%m-%dT%H:%M:%S%z"),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
        }
        for key in ("trace_id", "user_id"):        # 有就带上
            if hasattr(record, key):
                data[key] = getattr(record, key)
        if record.exc_info:
            data["exception"] = self.formatException(record.exc_info)
        return json.dumps(data, ensure_ascii=False)

    注入 trace_id 用 LoggerAdapter（自动往每条日志附带上下文）：

    class TraceAdapter(logging.LoggerAdapter):
    def process(self, msg, kwargs):
        kwargs.setdefault("extra", {}).update(self.extra)
        return msg, kwargs

# 每个请求创建一个带 trace_id 的 adapter
logger = TraceAdapter(logging.getLogger("app"), {"trace_id": "abc-123"})
logger.info("处理请求")   # 输出的 JSON 里自动带上 "trace_id": "abc-123"

    至于 structlog 和 loguru（学习目标里的"了解"项）：loguru 以"开箱即用、一行配置"著称，structlog 以"结构化日志优先"著称。它们解决的都是"让日志更好写、更结构化"，但底层很多实现仍复用标准库 logging 的 handler。先吃透标准库，再选第三方，才不会知其然不知其所以然。

    七、必做项目：企业级日志系统¶

    完整示例代码项目待补（示例代码/enterprise_logging/），本节先给设计 + 核心片段。

    7.1 需求¶

    实现一个企业级日志系统，支持：

    1. 控制台输出（给人看，带颜色/格式友好）。
    2. 文件输出（给排查用，UTF-8 编码）。
    3. JSON 格式（给日志平台解析）。
    4. Rotation 滚动切割（按大小）。

    7.2 核心实现¶

    import json
import logging
import logging.handlers

class JsonFormatter(logging.Formatter):
    # 见第六节

def build_logger(name="app") -> logging.Logger:
    logger = logging.getLogger(name)
    logger.setLevel(logging.INFO)
    logger.propagate = False          # 关键：避免传播到 root 造成重复

    # 1) 控制台：给人看
    console = logging.StreamHandler()
    console.setFormatter(logging.Formatter(
        "%(asctime)s %(levelname)s %(name)s: %(message)s",
        datefmt="%H:%M:%S"))
    logger.addHandler(console)

    # 2) 文件：按大小滚动
    file = logging.handlers.RotatingFileHandler(
        "app.log", maxBytes=10_000_000, backupCount=5, encoding="utf-8")
    file.setFormatter(logging.Formatter(
        "%(asctime)s %(levelname)s %(name)s %(filename)s:%(lineno)d: %(message)s"))
    logger.addHandler(file)

    # 3) JSON：给日志平台
    json_h = logging.handlers.RotatingFileHandler(
        "app.json.log", maxBytes=10_000_000, backupCount=5, encoding="utf-8")
    json_h.setFormatter(JsonFormatter())
    logger.addHandler(json_h)

    return logger

    7.3 验收标准（毕业标准）¶

    1. 三出口同时生效：一条日志同时出现在控制台、app.log（文本）、app.json.log（JSON）。
    2. Rotation 生效：把 maxBytes 调小，验证文件自动滚动出 app.log.1、app.log.2。
    3. 无重复输出：propagate = False 后，日志不会因为传播到 root 而打印两次。
    4. JSON 可解析：app.json.log 每一行都能被 json.loads 解析，且带 level、logger、message 字段。
    5. Trace ID 贯穿：用 LoggerAdapter 给同一请求的日志注入相同 trace_id，JSON 里能看到它。

    八、全章速查表¶

    知识点 一句话要点
    五级日志 DEBUG < INFO < WARNING < ERROR < CRITICAL（10~50）
    四大组件 Logger（入口）/ Handler（出口）/ Formatter（格式）/ Filter（细过滤）
    数据流 Logger 产生 → Handler 路由 → Formatter 格式化 → 输出
    getLogger(__name__) 每个模块一个 logger，名字即模块路径
    点号层级 app.module 的父是 app，向上到 root
    陷阱：propagate 默认 True，子 logger 配了 handler 会重复输出，需设 False
    陷阱：两道闸 logger 级别 + handler 级别都过了才输出
    RotatingFileHandler 按 maxBytes 滚动，backupCount 定保留数
    陷阱：logging.handlers 需显式 import logging.handlers
    Trace ID 同一次请求的日志共享一个 ID，用 LoggerAdapter 注入
    JSON Log 结构化输出，供日志平台解析检索
    structlog / loguru 第三方：开箱即用/结构化优先，底层多复用标准库

    九、贯穿全章的一条判断¶

    最后收束到这一章要建立的认知：

    日志不是"输出字符串"，而是"带上下文、分级别、可路由的事件流"。

    • 想要分清轻重、按需开关 → 用五级日志，别用 print。
    • 想要一条日志同时进控制台、文件、日志平台 → 一个 logger 挂多个 handler。
    • 想要生产环境能排查问题 → Trace ID 串起同一次请求，JSON 让日志可被平台解析。

    理解 logging 的标志，不是会 logging.info("xxx")，而是能说清楚：一条日志从 logger.info 到最后落盘经过了哪几道闸、propagate 为什么会导致重复、RotatingFileHandler 和 handlers 导入各有什么坑。这几点通了，后面做微服务的可观测性（OpenTelemetry、链路追踪）就有了地基。
