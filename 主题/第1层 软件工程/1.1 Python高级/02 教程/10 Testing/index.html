    Testing（★★★★★）¶

    目标：掌握 pytest 的四个核心机制——fixture 的作用域、parametrize 参数化、monkeypatch 替换外部依赖、mock 隔离外部系统，并能把测试覆盖率做到 90% 以上。

    一、为什么需要测试¶

    1.1 测试的价值¶

    测试不是"额外负担"，而是工程的安全网：

    1. 防止回归——改代码时，测试能立刻告诉你"哪里改坏了"。
    2. 文档作用——测试描述了一个函数"该怎么用、边界在哪"。
    3. 重构的底气——有测试覆盖，你才敢大胆重构而不担心破坏现有功能。

    没有测试的项目，每次改动都是一次"可能引爆线上"的赌博。

    1.2 pytest 的地位¶

    pytest 是 Python 事实标准的测试框架：语法简单（用原生 assert，不用记 assertEqual）、插件生态丰富（coverage、mock、asyncio 等）。unittest 是标准库自带的老框架（了解即可，风格较重）。

    二、pytest 基础¶

    2.1 测试发现与断言¶

    pytest 会自动发现 test_*.py 或 *_test.py 文件里 test_ 开头的函数。断言直接用原生 assert：

    # test_math.py
def add(a, b):
    return a + b

def test_add():
    assert add(1, 2) == 3
    assert add(-1, 1) == 0

    跑测试：

    pytest                    # 跑全部
pytest -v                 # 详细输出
pytest test_math.py       # 单个文件
pytest -k "add"           # 按关键字筛选

    2.2 用 assert，不是 assertEqual¶

    pytest 的杀手锏是直接用原生 assert，失败时它能自动展示表达式的值（不用像 unittest 那样为每种比较记一个断言方法）。这是 pytest 比 unittest 简洁的核心原因之一。

    三、fixture：复用测试准备¶

    3.1 什么是 fixture¶

    fixture 是"测试的前置准备"——测试需要的对象、数据、环境，用 fixture 统一创建，测试函数通过参数声明"我需要它"：

    import pytest

@pytest.fixture
def db_connection():
    conn = create_connection(":memory:")   # 准备
    yield conn                             # 交给测试
    conn.close()                           # 清理（测试结束后执行）

def test_query(db_connection):             # 参数名 = fixture 名
    assert db_connection.execute("SELECT 1") == 1

    yield 之前的代码是"准备"，之后的代码是"清理"（测试结束自动执行）。fixture 的核心价值是一处定义、多个测试复用，且自动清理。

    3.2 作用域：function / class / module / session¶

    fixture 默认作用域是 function（每个测试函数创建一个新实例）。可以用 scope= 调整：

    作用域 生命周期
    function（默认） 每个测试函数一次
    class 每个测试类一次
    module 每个模块一次
    session 整个测试会话一次

    实测区别（同一个计数器 fixture）：

    @pytest.fixture(scope="module")        # module 作用域
def module_counter():
    return {"count": 0}

def test_m1(module_counter):
    module_counter["count"] += 1
    assert module_counter["count"] == 1   # 第一个测试：1

def test_m2(module_counter):
    module_counter["count"] += 1
    assert module_counter["count"] == 2   # 同一个实例延续：2

    如果换成默认 function 作用域，test_m2 会拿到一个全新的计数器，count 还是 1。

    3.3 陷阱：作用域与状态泄漏¶

    作用域选错会导致状态泄漏：测试之间本应隔离，却因为共享了同一个 fixture 实例而互相影响（"前一个测试改了数据，后一个测试失败"）。经验法则：

    • 有状态的资源（数据库连接、可变对象）→ 用默认 function 作用域，保证测试隔离。
    • 昂贵的、无状态/只读的资源（启动一次的服务、加载一次的配置）→ 用 module/session 作用域，省时间。

    3.4 fixture 依赖¶

    fixture 可以依赖另一个 fixture（通过参数名）：

    @pytest.fixture
def config():
    return {"db": "postgres://..."}

@pytest.fixture
def db_connection(config):     # 依赖 config
    return create_connection(config["db"])

    依赖关系由参数名自动解析，可以层层组合。

    四、parametrize：参数化¶

    一个测试逻辑，多组输入输出，用 @pytest.mark.parametrize 一次声明：

    @pytest.mark.parametrize("a, b, expected", [
    (1, 2, 3),
    (0, 0, 0),
    (-1, 5, 4),
])
def test_add(a, b, expected):
    assert a + b == expected

    pytest 会把它展开成 3 个测试用例（test_add[1-2-3]、test_add[0-0-0]、test_add[-1-5-4]），任何一个失败都能单独定位到具体那组参数。边界值（0、负数、极大值、空串）是参数化的重点场景。

    五、monkeypatch：替换外部依赖¶

    测试时常要"换掉"某个函数或环境变量，又希望测试结束后自动还原。monkeypatch fixture 就是干这个的：

    def get_greeting():
    return "real"

def test_monkeypatch(monkeypatch):
    monkeypatch.setattr("模块名.get_greeting", lambda: "fake")  # 替换函数
    assert get_greeting() == "fake"

    monkeypatch.setenv("MY_ENV", "hello")                        # 设环境变量
    import os
    assert os.environ["MY_ENV"] == "hello"
    # 测试结束，monkeypatch 自动还原函数和环境变量

    monkeypatch 的价值在于自动还原——你不用写 try/finally 去恢复现场，测试之间也不会因为"上一个测试改了全局状态"而互相污染。

    六、mock：隔离外部系统¶

    6.1 Mock 对象¶

    unittest.mock.Mock 是"假的替身对象"——它接受任意调用、返回你指定的值，用于隔离外部系统（数据库、API、第三方服务），让单元测试不依赖真实外部环境：

    from unittest import mock

def test_mock():
    fake = mock.Mock(return_value=42)
    assert fake("任意参数") == 42     # 无论传什么，都返回 42
    fake.assert_called_once()          # 验证"确实被调用了一次"

    6.2 典型场景¶

    def fetch_and_process(client, url):
    data = client.get(url)             # 依赖外部 HTTP 客户端
    return data.upper()

def test_fetch(monkeypatch):
    fake_client = mock.Mock()
    fake_client.get.return_value = "hello"    # 让 get() 返回固定值
    assert fetch_and_process(fake_client, "http://x") == "HELLO"
    fake_client.get.assert_called_once_with("http://x")   # 验证参数

    这里 fetch_and_process 根本不需要真实网络——mock 替代了外部客户端，测试又快又稳，还能精确断言"用了什么参数调用了多少次"。

    6.3 mock 的边界¶

    mock 的坑在于过度 mock：如果 mock 掉了一切，测试就只剩"验证 mock 调用 mock"，测不出真实逻辑。经验法则：单元测试 mock 边界（外部系统），集成测试用真实组件。别为了 mock 而 mock。

    七、coverage：覆盖率¶

    覆盖率衡量"代码有多少行被测试执行到了"，用来发现没测到的死角。pytest 用 pytest-cov 插件：

    pip install pytest-cov
pytest --cov=你的包名 --cov-report=term-missing
# Name      Stmts   Miss  Cover
# mypkg.py     10      2    80%

    term-missing 会列出具体哪些行没被覆盖，是定位测试盲区的利器。覆盖率是"必要不充分"指标——覆盖率高不代表测得好（可能只是"执行到了"却没"断言正确"），但覆盖率低一定说明有没测的地方。

    八、持续测试：GitHub Actions¶

    测试只在本地跑是不够的——你没法保证每个协作者的机器上、每次合并前都跑过。CI（持续集成）把测试自动化：每次 push / 开 PR，GitHub Actions 自动拉起干净环境跑测试。

    # .github/workflows/test.yml
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v4
      - run: uv sync --extra dev
      - run: uv run pytest

    意义在于："测试通过"从"我的机器上通过"变成"任何人都能验证的客观事实"，坏代码在合并前就被拦下。

    九、必做项目：测试覆盖率 ≥ 90%¶

    完整示例代码项目待补（可直接复用 collection_lib / plugin_system 两个现成项目练手，它们已有测试）。

    9.1 需求¶

    给已有项目（如 collection_lib 或 plugin_system）补齐测试，使覆盖率 ≥ 90%，并接入 GitHub Actions 自动跑。

    9.2 步骤¶

    1. 用 pytest --cov 测出当前覆盖率，找到未覆盖的代码。
    2. 优先补核心逻辑和边界情况（空输入、极端值、异常路径）的测试。
    3. 用 fixture 抽公共准备、parametrize 覆盖多组边界、monkeypatch/mock 隔离外部依赖。
    4. 加 .github/workflows/test.yml，让每次 push 自动跑测试。

    9.3 验收标准（毕业标准）¶

    1. 覆盖率 ≥ 90%：pytest --cov 报告覆盖率达标。
    2. 测试真实有效：不是"只执行不断言"——每个测试都有明确的 assert 或行为验证。
    3. 边界覆盖：空值、0、负数、超长输入、异常路径都有对应测试。
    4. CI 通过：GitHub Actions 上测试绿灯，任何人 push 都能自动验证。
    5. 测试可维护：公共准备抽成了 fixture，重复的用例用 parametrize 收敛。

    十、全章速查表¶

    知识点 一句话要点
    断言 用原生 assert，不用 assertEqual
    fixture 测试前置准备，yield 前准备、后清理
    fixture 作用域 function/class/module/session，默认 function
    作用域陷阱 有状态资源用默认作用域，避免状态泄漏
    fixture 依赖 参数名引用另一个 fixture，自动解析
    parametrize 一组参数展开成多个用例，边界值必备
    monkeypatch 替换函数/环境变量，测试结束自动还原
    mock Mock 假替身隔离外部系统，可断言调用
    mock 陷阱 别过度 mock，边界用 mock、集成用真实组件
    coverage pytest-cov 测覆盖率，term-missing 看盲区
    覆盖率是必要不充分 高覆盖 ≠ 测得好，低覆盖一定没测到
    CI GitHub Actions 让"测试通过"成为客观事实

    十一、贯穿全章的一条判断¶

    最后收束到这一章要建立的认知：

    测试的本质，是用可重复的自动化，把"改代码会不会坏"这件靠运气的事，变成靠证据的事。

    • 想要敢改代码、敢重构 → 用 fixture + assert 写测试，覆盖率做安全网。
    • 想要测试稳定、不依赖外部环境 → 用 monkeypatch / mock 隔离边界，用 fixture 作用域管理隔离。
    • 想要坏代码在合并前被拦下 → 接入 GitHub Actions，让测试自动跑、客观通过。

    理解测试的标志，不是会写 assert 1 == 1，而是能说清楚：fixture 作用域为什么会影响测试隔离、monkeypatch 和 mock 各隔离什么、覆盖率为什么是必要不充分。这三点通了，你就从"写完代码手动点两下"进到了"写完代码测试替你兜底"的工程状态。
