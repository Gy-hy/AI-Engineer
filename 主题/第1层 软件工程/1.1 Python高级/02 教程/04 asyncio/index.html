    asyncio（★★★★★）¶

    目标：理解 asyncio 的并发本质——它是"单线程 + 协作式调度"，不是"多线程"。掌握协程、事件循环、任务与同步原语，并能手写一个 mini event loop 把黑盒打开。

    零、先纠正一个最要命的直觉错误¶

    很多人在学 asyncio 之前，是带着多线程的直觉来的：以为"异步 = 多线程"，以为 await 的地方会被"并发地同时执行"。这个直觉是错的，而且错得根本。

    asyncio 的真相是：

    asyncio = 单线程 + 协作式调度
    • 单线程：整个程序只有一个线程在执行你的协程代码，任意时刻只有一个协程在真正运行。
    • 协作式调度：协程之间通过 await 主动让出控制权，事件循环再把控制权交给下一个协程。没有"抢占"——不会被随时打断，除非它自己 await。

    所以下面这段代码里，A 和 B 是交错执行，不是同时执行。为了让"交错"肉眼可见，我让每个协程多个让出点，且每让出一次都打印一行：

    import asyncio

async def task(name):
    print(f"[{name}] 第 1 步")
    await asyncio.sleep(0)      # ← 让出控制权，事件循环去跑别的协程
    print(f"[{name}] 第 2 步")
    await asyncio.sleep(0)      # ← 再让出
    print(f"[{name}] 第 3 步")

async def main():
    await asyncio.gather(task("A"), task("B"))

asyncio.run(main())
# 输出（顺序固定，可复制到本地跑一遍验证）：
# [A] 第 1 步
# [B] 第 1 步
# [A] 第 2 步
# [B] 第 2 步
# [A] 第 3 步
# [B] 第 3 步

    看输出：A 走到「第 1 步」后，在 await asyncio.sleep(0) 处让出，事件循环才轮到 B 走「第 1 步」；B 让出后，A 接着走「第 2 步」……两个协程你一步、我一步地交错推进。这就是协作式调度——不是两个协程"同时"在跑，而是"轮流各前进一步"。

    这段代码到底是怎么跑的？ 把事件循环内部想象成两个清单——就绪队列（"我准备好了，下一个能跑"）和等待区（"我在 sleep，暂时别叫我"）。事件循环的工作就是：不断从就绪队列取一个出来跑，跑它到下一个 await，把它搬进等待区，再取下一个。下面是每一步的实时状态：

    步骤 0  gather 登记 A、B，但都还没跑
       就绪队列：[A, B]          等待区：（空）

步骤 1  取出 A 跑 → 打印 [A] 第 1 步 → 撞上 sleep(0)，A 让出
       就绪队列：[B]             等待区：A（睡 0 秒）

步骤 2  取出 B 跑 → 打印 [B] 第 1 步 → 撞上 sleep(0)，B 让出
       就绪队列：（空）          等待区：A、B（都在睡 0 秒）

步骤 3  sleep(0) 的 0 秒瞬间到期，A、B 被搬回就绪队列（A 先睡先醒，排前面）
       就绪队列：[A, B]          等待区：（空）

步骤 4  又取出 A → 打印 [A] 第 2 步 → 又 sleep(0) 让出
       就绪队列：[B]             等待区：A

步骤 5  取出 B → 打印 [B] 第 2 步 → 让出

步骤 6  取出 A → 打印 [A] 第 3 步（后面没有 await 了，A 跑完退出）
步骤 7  取出 B → 打印 [B] 第 3 步 → B 跑完退出，队列清空，循环结束

    从这份快照能读出三条规则：

    1. await = 从"就绪队列"搬进"等待区"。协程 await 那一刻就彻底停住，等 sleep 到期或 IO 完成，才被搬回就绪队列。
    2. "并发"就是这套"搬来搬去"在高速运转——没有任何东西"同时"跑，永远是"一个在跑，其余在排队或等待"。
    3. 没有 await 的协程会独占到底。如果某个协程里没有 await，它一旦被取出就一口气跑完，中间不让出，别的协程只能干等。这就是为什么 CPU 密集的计算放进 asyncio 会堵死整个循环——它不让出，别人永远轮不到。

    两个补充理解：

    1. asyncio.sleep(0) 就足以让出——睡眠时长是 0，但它仍然会"交一次控制权给事件循环"，让另一个就绪的协程有机会先跑。用来演示"让出"这个动作，sleep(0) 是最纯粹的选择，它不引入"睡了多久"的干扰。
    2. 想用"时间"来感受让出，就把 sleep 拉长。把上面每个 sleep(0) 改成 sleep(0.5)，运行后你会清楚地看到：两个"第 1 步"先出现，隔了半秒，两个"第 2 步"才出现——这就是"让出后要等一会儿才被恢复"。但拉长时间的同时要理解，此时它演示的已经不是"协作式切换"，而是"IO 等待期间 CPU 空闲"了。

    这条认知决定后面所有内容：理解"为什么 asyncio 能处理上万个并发连接""为什么 CPU 密集型任务放 asyncio 里没有加速效果"，全都从"单线程 + 协作式"这条根上长出来。

    一、四个必须分清的概念：同步 / 异步 / 阻塞 / 非阻塞¶

    这是学习目标里"理解"层次的内容，但它们是整个 asyncio 的基石，必须先钉死。

    1.1 同步 vs 异步——"谁在等，等的方式是什么"¶

    同步（Synchronous）：调用方发起调用后，原地等待结果返回，拿到结果才继续下一行。

    def download(url):
    ...  # 假设要花 1 秒

a = download(url1)   # 等 1 秒
b = download(url2)   # 再等 1 秒
# 总共 2 秒——第二个必须等第一个完全结束

    异步（Asynchronous）：调用方发起调用后不原地等，先去干别的，等结果"好了"再回来处理。

    async def download(url):
    ...

task1 = asyncio.create_task(download(url1))   # 发起，不等待
task2 = asyncio.create_task(download(url2))   # 发起，不等待
a = await task1    # 两个都在后台跑，这里才真正收结果
b = await task2
# 如果每个下载 1 秒，且时间都花在等网络上，总共可能只要 1 秒多一点

    1.2 阻塞 vs 非阻塞——"等待时，CPU/线程有没有被占住"¶

    这是最容易和"同步/异步"混淆的一对，但它们描述的是不同的维度：

    概念 描述的是 关键问题
    同步 / 异步 调用方的等待方式 调用方是原地等，还是先去干别的
    阻塞 / 非阻塞 操作本身的性质 操作在等待时，是否占住线程
    • 阻塞（Blocking）：操作会让当前线程停住，直到完成。比如 requests.get() 等网络响应时，线程就卡在那，什么都干不了。
    • 非阻塞（Non-blocking）：操作立刻返回，不等结果，线程可以继续干别的。

    1.3 IO 密集 vs CPU 密集——为什么这决定了 asyncio 有没有用¶

    这是最关键的分界，它决定了 asyncio 到底能加速什么、不能加速什么：

    • IO 密集（IO-bound）：程序的时间主要花在等待上——等网络响应、等磁盘读写、等数据库返回。等待期间 CPU 是空闲的。
    • CPU 密集（CPU-bound）：程序的时间主要花在计算上——循环、数学运算、图像处理。CPU 一直在满负荷跑。

    asyncio 只对 IO 密集有效，对 CPU 密集无效，甚至更糟：

    # IO 密集——asyncio 大显身手
# 下载 100 个网页，时间都花在等网络，单线程就能"看起来同时"等 100 个请求

# CPU 密集——asyncio 毫无帮助
async def compute():
    total = 0
    for i in range(10_000_000):
        total += i * i
    return total
# 这段纯计算会一直占着线程，期间不会让出（因为它内部没有一个 await），
# 单线程下它和普通同步代码一样慢，且会堵住其他所有协程
# （更精确的原因见 2.2 节"让出点在被 await 对象内部"）

    一句话总结这四个概念的关系：

    asyncio 的核心价值是——在一个线程里，用"非阻塞 + 异步"的方式，高效地"等待"大量 IO。IO 密集是它的主场，CPU 密集是它的禁区。

    二、协程（Coroutine）与 async / await¶

    2.1 async def 定义协程函数¶

    async def 定义的不是普通函数，而是协程函数（coroutine function）：

    async def hello():
    return "hi"

    关键区别——调用它不会执行函数体，而是返回一个协程对象：

    >>> hello()
<coroutine object hello at 0x...>    # 没执行！只是创建了协程对象
>>> import asyncio
>>> asyncio.run(hello())             # 这样才真正执行
'hi'

    这正是 asyncio 和普通函数的根本不同：普通函数一调用就执行，协程函数调用只创建对象，要等事件循环来驱动。

    直接调用协程函数而不 await 会怎样？ 会得到一个"从未被 await"的警告，函数体根本不会执行：

    async def main():
    hello()    # ❌ RuntimeWarning: coroutine 'hello' was never awaited

asyncio.run(main())

    2.2 await —— 让出控制权，并等待结果¶

    await 是协程里主动暂停自己、把控制权交回事件循环、并等待一个结果的语句：

    async def main():
    result = await some_coroutine()   # 暂停这里，去跑别的协程，等它完成再回来
    print(result)

    await 后面的对象必须是可等待对象（awaitable）——协程、Task、或实现了 __await__ 的对象。

    await 的本质（呼应学习目标"打通 Generator"的要求）：

    await 和生成器的 yield 是同一套底层机制——协程执行到 await，就相当于"在这里暂停，把控制权交出去"，等被等待的对象完成后，事件循环再把它恢复，继续 await 之后的代码。这一层关系会在第六节"手写 mini event loop"里彻底打开。

    await 到底做了什么——四个精确的动作¶

    await 可以被拆成四个动作，理解它们才能避开协程里最常见的误解：

    1. 暂停自己——当前协程停在这个 await 点上，不再往下执行；
    2. 交出控制权——把"事件循环下一步跑谁"的决定权还回去；
    3. 等待——等后面的那个可等待对象产出结果；
    4. 被唤醒拿结果——结果好了，协程被重新调度，await 表达式返回这个结果，继续往下。

    第一个要纠正的误解：await 让出的不是"线程"，是"控制权"。

    线程从头到尾只有一个（前面实验里 A、B、主协程打印的线程名全是 MainThread），它从来没有被"让出去"过。await 真正让出的，是"轮到谁跑"的决定权——线程还在跑，只是接下来执行哪段协程代码被重新调度了。

    一个线程（MainThread）
  └── 事件循环拿着"控制权"
        ├── 这一刻：执行协程 A 的代码
        ├── A 到了 await，交回控制权
        └── 下一刻：执行协程 B 的代码

    第二个要纠正的误解：让出点不在 await 这一行，而在"被 await 对象内部的第一个 await"。

    这是最关键、也最容易被忽略的细节。await 协程() 时，不是立刻让出，而是先"钻进"那个协程，一直执行到它内部第一个 await（或 return）才停：

    async def inner():
    print("进入 inner")
    await asyncio.sleep(1)   # ← 真正让出发生在这一行
    print("inner 结束")

async def outer():
    await inner()            # ← 这里先"钻进" inner，不是立刻让出

    执行顺序是：outer 执行到 await inner() → 先进入 inner，打印"进入 inner" → inner 执行到 await asyncio.sleep(1)，这一行才真正让出 → 1 秒后 inner 被唤醒，打印"inner 结束"，返回 → outer 的 await 拿到结果继续。

    所以——await 更像一个"推进器"，把执行流"压进"被等待的协程，直到那个协程自己停下来（内部遇到 await）或结束（return）。

    由此推出一个判断标准：一个协程会不会让出、能不能并发，看它内部有没有"真等待"。

    async def compute():
    total = 0
    for i in range(1_000_000):
        total += i
    return total        # 内部没有 await——它一旦被推进，就一路跑到底，不让出

async def outer():
    result = await compute()   # ← 不会让出，直接同步算完，和调普通函数一样

    compute 内部没有一个 await，所以 outer 的 await compute() 也全程不让出。这就是之前说的"CPU 密集会堵死循环"的精确原因：不是 async def 就堵，而是"这个协程内部没有让出点"。

    判断标准一句话：看它内部有没有 await（而且是 await 一个真正会让出的东西，比如 IO）。有，就会让出；没有，就是披着 async 外衣的同步函数。

    main 里的 await gather(...) 是干什么的¶

    最后补一个新手最容易漏掉的点——入口协程 main 里那个 await 的作用：

    async def main():
    await asyncio.gather(task("A"), task("B"))   # 这个 await 不能省

asyncio.run(main())

    asyncio.gather(...) 调用后返回一个"聚合协程对象"，它不会立刻执行。如果不用 await 驱动它，main 就直接走完、结束了，asyncio.run 一看入口结束了就关闭循环，A、B 根本来不及跑。

    所以这个 await 的作用是：让 main 在这里"撑住"，等 A、B 都跑完、拿到结果，再继续（或结束）。入口协程必须"撑住"整个程序直到所有子任务完成，await 就是那个"撑住"的动作。

    2.3 协程的三种常见形态¶

    # 1. 普通协程函数
async def fetch(url):
    return url

# 2. 协程里 await 协程
async def main():
    data = await fetch("http://example.com")

# 3. 协程里 await Task（并发）
async def main():
    task = asyncio.create_task(fetch("http://example.com"))
    data = await task

    三、事件循环（Event Loop）与 asyncio.run¶

    3.1 事件循环是什么¶

    事件循环是 asyncio 的心脏——一个无限循环，它的全部工作就是：

    1. 看看有没有协程准备好了（可运行）；
    2. 挑一个运行它，直到它 await 让出；
    3. 回到第 1 步，重复。
    事件循环 = 任务队列 + 一个 while 循环
循环体：
    从队列取出一个"就绪"的协程
    运行它，直到它 await 让出
    把它挂到"等待中"，继续下一个就绪协程

    这就是"单线程却能并发"的全部秘密：没有真正的同时执行，只有快速的轮流推进。因为切换发生在 await（让出点），而 IO 等待期间 CPU 是闲的，所以"轮流推进"能把空闲的 CPU 时间充分利用起来。

    3.2 asyncio.run() —— 启动事件循环的入口¶

    async def main():
    ...

asyncio.run(main())    # 创建事件循环 → 运行 main → 结束后关闭循环

    asyncio.run() 做了三件事：创建事件循环、把 main 协程跑完、关闭事件循环。它是程序唯一的异步入口——每个线程最多一个事件循环，asyncio.run() 不能嵌套调用。

    3.3 手动创建事件循环（了解）¶

    asyncio.run() 是高层封装，底层等价于：

    loop = asyncio.new_event_loop()       # 创建循环
try:
    loop.run_until_complete(main())   # 运行到 main 完成
finally:
    loop.close()                      # 关闭

    大多数场景用 asyncio.run() 就够了；手动管理循环只在库作者、或需要在特殊环境（如已有一个循环）下才需要。

    四、任务（Task）与并发：create_task / gather / wait¶

    4.1 create_task —— 把协程"安排"进事件循环¶

    前面说过，协程对象不会自己跑，必须被事件循环驱动。await 一个协程是"驱动它直到完成"，而 create_task 是"把它交给事件循环调度，我不在这里等"：

    async def main():
    task = asyncio.create_task(fetch("http://a.com"))   # 立刻返回，协程被调度
    # 主协程可以继续干别的
    result = await task    # 这里才真正等它完成、拿结果

    create_task 返回一个 Task 对象。Task 包装了一个协程，代表"这个协程已经在事件循环里被安排了"。

    关键——并发必须靠 create_task（或 gather），不能靠顺序 await：

    # ❌ 顺序执行——和同步一样慢
async def main():
    a = await fetch(url1)   # 等 url1 完成
    b = await fetch(url2)   # 才发起 url2
    # url1、url2 是串行的

# ✅ 并发执行
async def main():
    task1 = asyncio.create_task(fetch(url1))   # 先都安排上
    task2 = asyncio.create_task(fetch(url2))
    a = await task1
    b = await task2
    # url1、url2 在事件循环里交错推进，总耗时接近"最慢的那个"，而不是"两者之和"

    记住这条铁律：await 是"等"，create_task 是"安排"。想并发，先 create_task 安排，再 await 收结果。

    4.2 gather —— 并发执行一批协程¶

    gather 是 create_task 的便捷封装，一次性并发运行多个协程并收集结果：

    async def main():
    results = await asyncio.gather(
        fetch(url1),
        fetch(url2),
        fetch(url3),
    )
    # results = [结果1, 结果2, 结果3]，顺序与传入顺序一致

    gather 的行为细节（重要）：

    1. 结果顺序 = 传入顺序，不管谁先完成。
    2. 遇异常默认立即抛出——任何一个协程抛异常，gather 立刻抛出这个异常；其他协程不会被取消（它们继续在后台跑完，但结果被丢弃）。
    async def main():
    try:
        await asyncio.gather(ok_task(), bad_task())
    except ValueError as e:
        # 一旦 bad_task 抛 ValueError，这里立刻捕获
        # 但 ok_task 还在后台继续跑
    1. 想"一个失败不影响其他"，用 return_exceptions=True：
    results = await asyncio.gather(
    task1(), task2(), task3(),
    return_exceptions=True,    # 异常作为结果返回，而不是抛出
)
# 此时 results 里可能有正常结果，也可能有异常对象

    4.3 wait —— 更底层的控制（含一个版本陷阱）¶

    gather 适合"等全部完成、要结果"的场景。wait 提供更细的控制——它返回 (done, pending) 两个集合，让你知道哪些完成了、哪些还没：

    async def main():
    t1 = asyncio.create_task(fetch(url1))
    t2 = asyncio.create_task(fetch(url2))
    done, pending = await asyncio.wait([t1, t2])
    # done    —— 已完成的 Task 集合
    # pending —— 还没完成的 Task 集合

    ⚠️ 版本陷阱（Python 3.11+ 必知）：wait 不接受裸协程，必须传 Task。

    # ❌ Python 3.11+ 直接报 TypeError
done, pending = await asyncio.wait([fetch(url1), fetch(url2)])
# TypeError: Passing coroutines is forbidden, use tasks explicitly.

# ✅ 正确——先 create_task 再传
t1 = asyncio.create_task(fetch(url1))
t2 = asyncio.create_task(fetch(url2))
done, pending = await asyncio.wait([t1, t2])

    wait 的另一个优势——return_when 控制返回时机：

    done, pending = await asyncio.wait(
    [t1, t2, t3],
    return_when=asyncio.FIRST_COMPLETED,   # 有一个完成就返回
)
# 此时 done 里有 1 个，pending 里有 2 个——你可以先处理完成的，再继续等

    gather vs wait 选择：

    gather wait
    用途 并发执行 + 收集结果 细粒度控制"谁完成谁没完成"
    异常处理 默认立即抛（可 return_exceptions） 不抛，异常存在 task.exception() 里
    返回 结果列表（按顺序） (done, pending) 集合
    传参 直接传协程 必须传 Task（3.11+）

    经验法则： 大多数"并发一批任务、要全部结果"的场景用 gather 就够了；需要"先完成先处理""超时中止""部分失败不中断"时，用 wait。

    五、同步原语：Lock / Semaphore / Event / Queue¶

    asyncio 有自己的同步原语，和多线程的那套同名但完全不同——它们是协作式的，不会真的阻塞线程。

    5.1 Lock —— 协程间的互斥¶

    保护"同一时刻只能一个协程访问"的共享资源：

    lock = asyncio.Lock()

async def transfer(account, amount):
    async with lock:          # 同一时刻只有一个协程能进入
        await account.modify(amount)

    关键认知（呼应学习目标的线程安全纠正）： 纯 asyncio 单线程里，普通的共享变量其实不需要加锁——因为任意时刻只有一个协程在跑，不会被中途打断。那 Lock 有什么用？用于保护"跨越 await 的临界区"：

    counter = 0

async def increment():
    global counter
    tmp = counter          # 读
    await asyncio.sleep(0) # ← await 让出！另一个协程可能在这里改 counter
    counter = tmp + 1      # 写——此时 tmp 可能已经过时

    counter = counter + 1 如果不是原子操作（中间夹了 await），就需要 Lock 保证"读→改→写"不被其他协程插进来。这个细节在第六节的线程安全部分会展开。

    5.2 Semaphore —— 限制并发数量¶

    Semaphore 是"允许最多 N 个协程同时进入"的闸门，用来限流：

    sem = asyncio.Semaphore(3)    # 最多 3 个并发

async def download(url):
    async with sem:           # 超过 3 个时，第 4 个会在这里等待
        return await fetch(url)

async def main():
    urls = [f"http://example.com/{i}" for i in range(100)]
    await asyncio.gather(*(download(u) for u in urls))
    # 100 个下载任务，但同时最多 3 个在跑——这就是"限流"

    为什么限流重要： 如果无脑对 10000 个 URL 全部 create_task，会瞬间创建 10000 个并发连接，可能打爆目标服务器（被当成攻击）、耗尽本机文件描述符。Semaphore 让并发数可控。

    5.3 Event —— 协程间的"信号"¶

    Event 让一个协程"等"另一个协程"发信号"：

    event = asyncio.Event()

async def waiter():
    print("等待事件...")
    await event.wait()      # 阻塞直到 event.set()
    print("事件触发了！")

async def setter():
    await asyncio.sleep(1)
    event.set()             # 发信号，唤醒所有等待者

    5.4 Queue —— 协程间的数据管道¶

    Queue 是生产者-消费者模式的载体：

    queue = asyncio.Queue(maxsize=10)

async def producer():
    for i in range(100):
        await queue.put(i)      # 队列满了会等待
        print(f"生产 {i}")

async def consumer():
    while True:
        item = await queue.get()   # 队列空了会等待
        print(f"消费 {item}")
        queue.task_done()

async def main():
    producers = [asyncio.create_task(producer()) for _ in range(3)]
    consumers = [asyncio.create_task(consumer()) for _ in range(2)]
    await asyncio.gather(*producers)
    await queue.join()    # 等所有任务被消费完

    Queue 的 put / get 在"满/空"时不会阻塞线程，而是让协程挂起等待——这正是"协作式"的体现。

    六、打通三件事：yield、手写事件循环、线程安全¶

    这是学习目标里明确要求的「新增内容」——把 Context Manager、Generator 与 asyncio 用同一个机制串起来。理解这一节，才真正理解 asyncio 的原理，而不只是会用 API。

    6.1 协程和生成器是同一个底层机制¶

    回顾 Generator 章节的 yield：生成器函数执行到 yield 会暂停，把值交出去，下次 next() 再恢复。

    协程的 await 和它是同一个机制：

    生成器 协程
    暂停的关键字 yield await
    暂停时交出的 一个值 控制权
    谁来恢复 调用 next() 的人 事件循环
    语义 "惰性地吐出数据" "等一个结果，先干别的"

    两者底层都是"函数执行到一半可以暂停，之后被恢复"。这就是为什么学习目标里说"@contextmanager 里的 yield、生成器里的 yield、协程里的 await，用的是同一套机制"。

    6.2 手写一个 mini event loop¶

    不用 asyncio，自己实现一个极简版事件循环，把 asyncio.run 的黑盒打开：

    from collections import deque

class MiniEventLoop:
    def __init__(self):
        self.ready = deque()     # 就绪任务队列

    def create_task(self, coro):
        """把一个协程包装成任务，放进就绪队列。"""
        task = self._Task(coro)
        self.ready.append(task)
        return task

    def run(self):
        """循环调度：取出一个就绪任务，推进它，直到它让出。"""
        while self.ready:
            task = self.ready.popleft()
            try:
                # 推进任务——等价于 next()，让协程跑到下一个 await 点
                task.step()
            except StopIteration:
                pass          # 协程跑完了
            else:
                self.ready.append(task)   # 还没跑完，放回队列继续等

    class _Task:
        def __init__(self, coro):
            self.coro = coro

        def step(self):
            """让协程前进到下一个暂停点。"""
            next(self.coro)   # 简化版：协程里 await 的都得是"立即就绪"的东西


# 用这个 mini 循环跑两个协程
def task(name):
    print(f"[{name}] A")
    yield            # ← 让出，模拟 await
    print(f"[{name}] B")
    yield            # ← 再让出
    print(f"[{name}] C")

loop = MiniEventLoop()
loop.create_task(task("1"))
loop.create_task(task("2"))
loop.run()
# 输出：
# [1] A
# [2] A
# [1] B
# [2] B
# [1] C
# [2] C

    看输出：两个任务交错执行，1 走到第一个 yield 让出，2 走，再回到 1……这就是协作式调度的全部真相。

    这个 mini loop 揭示了三个本质：

    1. "并发"就是快速轮流推进——没有真正的并行，只有"每个任务前进一小步就换下一个"。
    2. await 就是 yield 的换皮——暂停自己、交出控制权、之后被恢复。
    3. 为什么 IO 密集才有效——真正的 asyncio 里，协程 await 一个 IO 操作时，事件循环会把它挂到"等待 IO 完成"，不占用 CPU 去轮询（底层用 epoll/select 等系统调用），所以一个线程能同时"等"上万个 IO。而 mini loop 简化成了"立即就绪"，没体现这层，但调度骨架是一样的。

    6.3 线程安全——asyncio 内部 vs 与多线程混用¶

    学习目标特别要求纠正一个认知，这里完整讲清：

    纯 asyncio 内部，普通共享变量不需要加锁。

    因为单线程 + 协作式，任意时刻只有一个协程在跑，不会"运行到一半被另一个线程打断"。这和"多线程必须处处加锁"的直觉相反：

    # 纯 asyncio 里，这段是安全的——不会被中途打断
counter = 0

async def increment():
    global counter
    counter += 1        # 没有 await 夹在中间，这句是"原子"的

    但有两种情况线程安全问题会重新出现：

    （a）临界区跨越了 await。 如果"读→改→写"中间夹了 await，另一个协程可能插进来，就需要 asyncio.Lock：

    counter = 0
lock = asyncio.Lock()

async def increment():
    global counter
    async with lock:               # 锁住跨越 await 的临界区
        tmp = counter
        await asyncio.sleep(0)     # ← 让出，没锁的话这里会被打断
        counter = tmp + 1

    （b）asyncio 和真正的多线程混用。 一旦用 loop.run_in_executor 跑阻塞的同步代码、或从另一个线程往事件循环塞任务，就真的涉及多线程了，此时必须用线程安全的接口：

    # 从另一个线程往事件循环塞任务——必须用 call_soon_threadsafe
loop.call_soon_threadsafe(callback, args)

# 在 asyncio 里跑阻塞的同步代码——用 run_in_executor 丢到线程池
result = await loop.run_in_executor(None, blocking_function, arg)

    总结这条认知： "异步 = 多线程"是完全错误的。asyncio 内部是"协作式单线程"，共享变量天然安全；只有在"跨越 await 的临界区"或"asyncio 与真线程混用"这两种边界情况，才需要引入锁和线程安全接口。

    七、超时与取消：timeout / Cancellation¶

    7.1 asyncio.timeout —— 给操作加超时¶

    Python 3.11+ 提供了 asyncio.timeout（更早版本用 asyncio.wait_for）：

    async def main():
    try:
        async with asyncio.timeout(5):       # 5 秒超时
            result = await slow_operation()
    except TimeoutError:
        print("超时了")

    关键事实（3.11+）：asyncio.TimeoutError 就是内建的 TimeoutError——两者是同一个类，所以 except TimeoutError 就能捕获。这也是 3.11 的一个简化：更早版本需要 except asyncio.TimeoutError。

    旧的 asyncio.wait_for（仍然可用）：

    result = await asyncio.wait_for(slow_operation(), timeout=5)
# 超时抛 asyncio.TimeoutError（= TimeoutError），且会取消 slow_operation

    7.2 取消（Cancellation）¶

    取消一个正在运行的任务：

    async def main():
    task = asyncio.create_task(long_running())
    await asyncio.sleep(1)
    task.cancel()          # 请求取消
    try:
        await task
    except asyncio.CancelledError:
        print("任务被取消了")

    三个必须知道的事实：

    事实一：CancelledError 不是 Exception 的子类，是 BaseException 的子类（Python 3.8+）。

    issubclass(asyncio.CancelledError, Exception)       # False
issubclass(asyncio.CancelledError, BaseException)   # True

    这意味着——普通的 except Exception 捕不到它：

    try:
    await task
except Exception as e:       # ❌ 捕不到 CancelledError！
    ...
except asyncio.CancelledError:
    ...                      # ✅ 必须单独捕，或用 except BaseException

    事实二：取消时要在清理后重新 raise。 如果你在 except CancelledError 里做了清理却不重新抛出，取消就被"吞掉"了，任务会装作正常继续，这是 bug：

    async def work():
    try:
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        await cleanup()      # 清理资源
        raise                # ✅ 必须重新抛出，让取消真正生效

    事实三：取消是"协作式"的。 取消只是请求——它向任务抛一个 CancelledError，任务得自己响应（在 await 处让出时才会收到）。一个纯 CPU 计算、从不 await 的协程是无法被取消的，因为它永远不让出控制权。

    async def uncancellable():
    while True:
        x = 1 + 1    # 从不 await，永远不让出——cancel() 也停不下来

    八、异步网络：aiohttp 与 httpx.AsyncClient¶

    asyncio 自己不能发网络请求，需要异步 HTTP 库。学习目标列出两个：aiohttp（必学）和 httpx.AsyncClient。

    8.1 aiohttp —— 老牌异步 HTTP 库¶

    import aiohttp
import asyncio

async def fetch(session, url):
    async with session.get(url) as response:
        return await response.text()

async def main():
    async with aiohttp.ClientSession() as session:
        html = await fetch(session, "https://example.com")
        print(html[:100])

asyncio.run(main())

    关键点：ClientSession 必须复用，不能每次请求新建。 一个 session 维护一个连接池（connection pool），复用它才能享受 HTTP keep-alive 的连接复用。如果每个请求都 ClientSession()，连接复用就失效了，性能大幅下降。

    8.2 httpx.AsyncClient —— 更现代的异步 HTTP 库¶

    import httpx
import asyncio

async def main():
    async with httpx.AsyncClient() as client:
        response = await client.get("https://example.com")
        print(response.text[:100])

asyncio.run(main())

    httpx 的优势是同步和异步 API 高度一致（httpx.Client 是同步版，httpx.AsyncClient 是异步版），且功能比 aiohttp 更现代（支持 HTTP/2、更好的类型标注）。

    选型经验：

    aiohttp httpx
    定位 专门的异步库 同步/异步双 API
    成熟度 更老、生态更大 更现代
    HTTP/2 需额外配置 原生支持
    学习曲线 异步专用 与 requests 风格接近

    两者都能胜任异步下载。本教程的项目用 aiohttp（学习目标把它列为必学），但 httpx.AsyncClient 是同样值得掌握的现代替代。

    九、Project 4：异步下载器¶

    9.1 项目目标¶

    学习目标要求实现一个异步下载器，支持：并发下载、限流、Retry、Progress Bar、Cancel。这正是 asyncio 所有知识点（并发、Semaphore、超时、取消、异步网络）的集大成。

    9.2 完整实现¶

    import asyncio
import aiohttp

class AsyncDownloader:
    def __init__(self, concurrency: int = 5, retries: int = 3):
        self.concurrency = concurrency
        self.retries = retries
        self.semaphore = asyncio.Semaphore(concurrency)   # 限流

    async def download_one(self, session, url):
        """下载单个 URL，带重试。"""
        for attempt in range(self.retries):
            try:
                async with self.semaphore:      # 限流：最多 concurrency 个并发
                    async with session.get(url) as resp:
                        resp.raise_for_status()
                        return await resp.read()
            except Exception:
                if attempt == self.retries - 1:
                    raise                       # 最后一次也失败，放弃
                await asyncio.sleep(2 ** attempt)  # 退避重试：1s, 2s, 4s
        return None   # 理论上到不了这里

    async def download_all(self, urls):
        async with aiohttp.ClientSession() as session:
            tasks = [asyncio.create_task(self.download_one(session, u))
                     for u in urls]
            return await asyncio.gather(*tasks, return_exceptions=True)

    async def download_with_cancel(self, urls):
        """支持 Ctrl+C 取消的版本。"""
        async with aiohttp.ClientSession() as session:
            tasks = [asyncio.create_task(self.download_one(session, u))
                     for u in urls]
            try:
                return await asyncio.gather(*tasks)
            except asyncio.CancelledError:
                # 取消所有任务，做清理
                for t in tasks:
                    t.cancel()
                raise

# 使用
async def main():
    downloader = AsyncDownloader(concurrency=5, retries=3)
    urls = [f"https://example.com/file/{i}" for i in range(50)]
    results = await downloader.download_all(urls)

asyncio.run(main())

    9.3 每个特性的实现要点¶

    特性 用到的知识点 实现位置
    并发下载 create_task + gather download_all 里所有任务先创建，再 gather
    限流 Semaphore download_one 里 async with self.semaphore
    Retry 循环 + 指数退避 download_one 的 for attempt in range(retries)
    Progress Bar 计数器 + 回调（或 tqdm） 每完成一个就更新进度（见下）
    Cancel CancelledError + task.cancel() download_with_cancel

    Progress Bar 的补充——用 tqdm（同步库，但可以在异步里通过 as_completed 配合更新）：

    from tqdm import tqdm

async def download_with_progress(self, urls):
    async with aiohttp.ClientSession() as session:
        tasks = [asyncio.create_task(self.download_one(session, u))
                 for u in urls]
        results = []
        # as_completed：谁先完成谁先返回，用于实时更新进度
        with tqdm(total=len(urls)) as pbar:
            for coro in asyncio.as_completed(tasks):
                result = await coro
                results.append(result)
                pbar.update(1)      # 每完成一个，进度条 +1
        return results

    asyncio.as_completed 是"谁先完成谁先出"的迭代器，配合 tqdm 就能实时刷新进度。

    9.4 验收标准（毕业标准）¶

    1. 真并发：用 create_task + gather，不是顺序 await。验证方式——对比"顺序下载 N 个文件"和"并发下载 N 个文件"的耗时，并发应显著更快。
    2. 限流生效：把 concurrency 设成 1，和设成 10 对比，能观察到并发被限制（用日志或计数器验证同一时刻最多 concurrency 个请求）。
    3. Retry 生效：故意用一个会偶发失败的 URL，观察它能自动重试、退避后成功。
    4. 可取消：运行中途按 Ctrl+C，程序能优雅退出（清理已创建的连接和任务），不留下僵尸任务或报错堆栈。
    5. Progress Bar：下载时能看到实时进度。
    6. 对比验证：写一个同步版本（用 requests）和异步版本（用 aiohttp）下载同样的 50 个 URL，记录耗时，理解 asyncio 对 IO 密集任务的加速。

    十、全章速查表¶

    知识点 一句话要点
    asyncio 本质 单线程 + 协作式调度，不是多线程
    同步/异步 调用方是原地等，还是先去干别的
    阻塞/非阻塞 操作等待时是否占住线程
    IO/CPU 密集 asyncio 只加速 IO 密集，对 CPU 密集无效
    async def 定义协程函数；调用它不执行，返回协程对象
    await 唯一让出控制权的语句；本质就是 yield 的换皮
    事件循环 任务队列 + 循环调度，asyncio 的心脏
    asyncio.run 启动/关闭事件循环的标准入口
    create_task 把协程安排进循环，不等待；并发的前提
    gather 并发执行 + 收集结果；结果按传入顺序
    wait 返回 (done, pending)；3.11+ 必须传 Task
    Lock 保护"跨越 await 的临界区"
    Semaphore 限制并发数——限流的工具
    Event 协程间"等信号/发信号"
    Queue 生产者-消费者管道
    asyncio.timeout 超时（3.11+）；TimeoutError 就是内建 TimeoutError
    CancelledError 是 BaseException 子类；取消后清理必须 raise
    取消是协作式 只在 await 让出点生效；纯 CPU 协程无法取消
    aiohttp 老牌异步 HTTP；ClientSession 必须复用
    httpx.AsyncClient 现代异步 HTTP，同步/异步 API 一致

    十一、贯穿全章的一条判断¶

    最后收束到学习目标反复强调的那句话：

    asyncio 的价值，是用"协作式单线程"高效地"等待"大量 IO；它不产生真正的并行，只是把空闲的等待时间填满。

    • 想要并发地等 IO（下载、请求、数据库查询）→ asyncio 是利器，单线程能扛上万个连接。
    • 想要并行地做计算（CPU 密集）→ asyncio 帮不上忙，去用 multiprocessing 或 concurrent.futures 的多进程/多线程。
    • 想要不写锁、共享变量天然安全 → 纯 asyncio 满足你；但一旦跨越 await 的临界区、或和真线程混用，锁和线程安全接口就得回来。

    真正理解 asyncio 的标志，不是会背 async/await 的语法，而是能说清楚：为什么它单线程却能并发、为什么它对 IO 有效对 CPU 无效、为什么它内部不需要锁。第六节手写 mini event loop，就是为了让你从"会调 API"走到"懂原理"。
