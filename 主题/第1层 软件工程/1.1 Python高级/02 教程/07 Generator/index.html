    Generator（★★★★★）¶

    目标：理解生成器的完整机制——yield 为什么能让函数"暂停-恢复"，send 和 yield from 各自解决什么问题，以及惰性求值如何让你写出内存安全的数据流水线。

    一、迭代器：生成器的地基¶

    1.1 可迭代 vs 迭代器¶

    要理解生成器，先分清两个常被混用的概念：

    • 可迭代（iterable）：能被 for 遍历、能传给 iter() 的对象——list、str、dict、tuple、set、文件对象、生成器。
    • 迭代器（iterator）：实现了 __next__ 的对象，能不断"吐出下一个值"，耗尽后抛 StopIteration。

    两者不是一回事：list 是可迭代，但不是迭代器（iter([1,2]) 才得到一个迭代器）；文件对象和生成器两者都是。for 循环的底层，就是不断调 iter(x) 拿迭代器、再调 next(it) 直到 StopIteration。

    1.2 __iter__ / __next__ 协议¶

    一个对象只要实现了 __iter__（返回迭代器）和 __next__（返回下一个值），就能被 for 遍历：

    class Countdown:
    def __init__(self, n):
        self.n = n
    def __iter__(self):
        return self          # 自己就是迭代器
    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1

for x in Countdown(3):
    print(x)   # 3, 2, 1

    1.3 陷阱：迭代器只能走一遍¶

    迭代器是"一次性"的——耗尽之后再迭代就是空的（实测）：

    def gen2():
    yield 1
g2 = gen2()
list(g2)   # [1]
list(g2)   # []  ← 已耗尽，第二次是空的

    这和 list 可以反复遍历形成鲜明对比。工程上的含义是：如果你要多次遍历，要么存成 list，要么每次重新生成。拿到一个迭代器就想当然地复用，是最常见的 bug 之一。

    二、生成器：用 yield 写迭代器¶

    2.1 两种生成器¶

    • 生成器函数：函数体里含 yield 的函数。调用它返回一个生成器对象。
    • 生成器表达式：把列表推导的 [] 换成 ()，即 (x*x for x in range(10))。

    两者本质相同，都是"惰性地、一个一个地产出值"。

    2.2 yield 的暂停-恢复语义¶

    yield 和 return 的关键区别：return 结束函数，yield 只是暂停。函数执行到 yield，把值交出去、停在原地、记住所有局部变量；下次 next() 时，从 yield 的下一行继续执行：

    def gen():
    print("开始")
    yield 1        # 暂停在这一点，返回 1
    print("继续")   # 下次 next() 从这里恢复
    yield 2

    这个"暂停-恢复"机制，正是第五章 @contextmanager 和第四章 asyncio 里协程共用的底层机制——它们本质上都是生成器语义的不同应用。这里讲的 yield 是"持续产出一串数据"，和 @contextmanager 里"只产出一次资源"是同一机制的两种语义，务必对照理解。

    2.3 陷阱：调用生成器函数不执行函数体¶

    gen() 调用不会执行函数体，只是返回一个生成器对象；只有第一次 next()（或 for 开始）才会真正执行到第一个 yield（实测）：

    g = gen()        # 这行不打印"开始"
next(g)          # 这行才打印"开始"，并返回 1

    很多人以为 gen() 会立刻干活，结果发现函数体"没执行"——它确实没执行，这是生成器的惰性特性，不是 bug。

    三、yield 的三种用法¶

    3.1 yield：产出值¶

    最基础的形式，上面已经讲过——把值一个一个交出去。

    3.2 send：向生成器传值¶

    yield 不仅可以往外吐值，还可以接收值。send(v) 会把 v 作为当前 yield 表达式的返回值，让生成器继续执行：

    def accumulator():
    total = 0
    while True:
        v = yield total     # 右侧 yield 吐出 total；左侧 v 接收 send 进来的值
        if v is None:
            break
        total += v

acc = accumulator()
next(acc)         # 必须先启动，返回 0
acc.send(10)      # v=10 → total=10，返回 10
acc.send(20)      # v=20 → total=30，返回 30

    注意两点：

    1. 第一次必须用 next()（或 send(None)）启动——因为生成器还没走到第一个 yield，没有地方可以接收值。
    2. yield total 这个表达式的值，由下一次 send 传入。所以 yield 既是"出口"（往外吐 total），又是"入口"（接收 send 的值）。

    send 是协程的基础——asyncio 里那个"能暂停、能被驱动、能传值"的协程，底层就是这套 send/yield 机制。

    3.3 yield from：委托子生成器¶

    yield from 把一个生成器的产出"委托"给另一个生成器，相当于 for x in sub: yield x 的简写，但功能更强：

    def sub():
    yield "a"
    yield "b"

def main():
    yield "start"
    yield from sub()    # 把 sub() 的产出原样转发
    yield "end"

list(main())   # ['start', 'a', 'b', 'end']

    yield from 更强的地方在于：子生成器的 return 值会成为 yield from 表达式的值：

    def sub():
    yield 1
    return "子生成器的结果"

def main():
    result = yield from sub()      # result 拿到子生成器的 return 值
    yield f"拿到: {result}"

list(main())   # [1, '拿到: 子生成器的结果']

    这个特性让 yield from 不仅能转发数据，还能向上传递子任务的结果——这在协程链里是核心能力。

    四、惰性求值：Lazy Loading¶

    4.1 为什么惰性¶

    生成器只在需要时才计算下一个值。这带来两个好处：

    1. 省内存——不需要一次性把全部结果算出来放进内存。
    2. 支持无限序列——因为不需要"先全部算完"，所以可以表示无穷的数据流。

    4.2 内存对比（实测）¶

    import sys
lst = [x * x for x in range(1_000_000)]   # 列表推导：一次性全算出来
gen = (x * x for x in range(1_000_000))   # 生成器表达式：惰性

sys.getsizeof(lst)   # 约 8,448,728 字节（8MB+，一百万个数全在内存）
sys.getsizeof(gen)   # 200 字节（几乎不占内存）

    同样是"一百万个数"，列表推导立刻吃掉 8MB 内存，生成器只占 200 字节、用的时候才一个个算。处理大文件、大结果集时，这个差距就是"内存溢出"和"平稳运行"的区别。

    4.3 无限序列¶

    惰性让"无穷"成为可能：

    def count():
    n = 0
    while True:
        yield n
        n += 1

c = count()
[next(c) for _ in range(5)]   # [0, 1, 2, 3, 4]——无限序列，按需取用

    没有惰性，"无限序列"这个概念根本不存在——任何"先把所有值算出来"的写法都会卡死在无限循环或内存耗尽里。

    五、应用：Streaming / Pipeline / Lazy Loading¶

    5.1 Pipeline：用生成器串起数据流水线¶

    生成器最强大的应用是管道（pipeline）——每个生成器只做一件事（过滤、转换、聚合），用 yield 把结果传给下一个。像 Unix 管道一样，数据边流边处理：

    def read_lines(source):
    """Source：产出原始行。"""
    for line in source:
        yield line

def grep(lines, pattern):
    """Filter：只放行匹配的行。"""
    for line in lines:
        if pattern in line:
            yield line

def transform(lines):
    """Transform：加工每一行。"""
    for line in lines:
        yield line.strip().upper()

# 组合成一条流水线：读取 → 过滤 → 转换
lines = read_lines(open("app.log"))
errors = grep(lines, "ERROR")
result = transform(errors)
for line in result:
    print(line)

    关键点：数据不是一次性读进来的，而是每 for 迭代一次，就沿整条管道流动一次。即使 app.log 有 10GB，内存占用也只有"当前处理的一行"。

    5.2 流式处理大文件¶

    def count_lines(path):
    with open(path) as f:
        for line in f:      # 文件对象本身是可迭代的，逐行产出
            yield line

# 逐行统计，不会把整个文件读进内存
total = sum(1 for _ in count_lines("huge.log"))

    六、必做项目：日志流处理器¶

    完整示例代码项目待补（示例代码/log_stream/），本节先给设计 + 核心片段，可直接内联验证。

    6.1 需求¶

    实现一个日志流处理器，支持：

    1. 无限读取——像 tail -f 一样跟随一个持续写入的日志文件，没有新行时等待。
    2. Pipeline——多个处理阶段（source → filter → transform）用生成器串联。
    3. Filter——按关键字过滤（如只保留含 ERROR 的行）。
    4. Transform——对每行做加工（如大写、加行号、解析字段）。

    6.2 核心实现¶

    import time

def tail_follow(path):
    """Source：无限跟随日志文件（tail -f 语义）。"""
    with open(path) as f:
        f.seek(0, 2)                 # 先移到文件末尾，只处理新写入的行
        while True:
            line = f.readline()
            if line:
                yield line.rstrip("\n")
            else:
                time.sleep(0.1)      # 暂无新行，稍等再试

def grep(pattern):
    """Filter：返回一个"只放行匹配行"的生成器。"""
    def filter_gen(lines):
        for line in lines:
            if pattern in line:
                yield line
    return filter_gen

def transform(lines):
    """Transform：对每行做加工。"""
    for line in lines:
        yield f"[{len(line)}] {line.upper()}"

    Pipeline 组合：

    source = tail_follow("app.log")
errors = grep("ERROR")(source)   # 只保留 ERROR 行
output = transform(errors)       # 加工每一行

for line in output:              # 逐行流式处理
    print(line)

    这个设计里，grep 是"参数化 Filter"（返回一个生成器的函数，可以理解为生成器版的装饰器工厂），tail_follow 是无限流，transform 是纯转换——恰好覆盖了 yield、惰性、无限序列、Pipeline 四大能力。

    6.3 验收标准（毕业标准）¶

    1. 无限读取生效：向日志文件追加新行，程序能自动处理新行；不追加时程序等待而不退出。
    2. Filter 生效：混有 INFO/ERROR 的日志，只输出含 ERROR 的行。
    3. Transform 生效：输出行带上了行号/大写等加工痕迹。
    4. Pipeline 组合正确：三个生成器串联后，数据按 source → filter → transform 的顺序流动，且是逐行流式的（用内存监控验证处理大文件时内存不暴涨）。
    5. 惰性验证：对比"用 list 一次性读入"和"用生成器流式处理"同一大文件的内存占用，流式应远小于前者。

    八、贯穿全章的一条判断¶

    最后收束到这一章要建立的认知：

    生成器的核心，是"惰性"+"暂停-恢复"——yield 让函数能停住、记住状态、按需产出，从而把"数据"变成"数据流"。

    • 想要处理大文件、大结果集不爆内存 → 用生成器流式处理，别用 list 一次性全读进来。
    • 想要多个处理阶段清晰解耦（读→过滤→转换）→ 每个阶段一个生成器，串成 Pipeline。
    • 想要理解 asyncio 协程的底层 → yield/send 这套暂停-恢复-传值机制就是协程的原型。

    理解生成器的标志，不是会写 yield，而是能说清楚：为什么调用生成器函数不执行、迭代器为什么只能走一遍、send 的值从哪来、yield from 的返回值到哪去。这四点通了，"惰性求值"和"数据流水线"就不再是抽象概念，而是你随手就能写出来的工程能力。
