    Performance（★★★★★）¶

    目标：建立"先测量、后优化"的性能方法论——用 timeit 做微基准、cProfile 定位热点，再针对 CPU/Memory/IO 三类瓶颈选择正确的优化手段，把性能提升做到有据可依。

    一、性能优化的前提：先测量，后优化¶

    1.1 过早优化是万恶之源¶

    Donald Knuth 的著名论断——"premature optimization is the root of all evil"（过早优化是万恶之源）——完整的语境是：大约 97% 的时候，你不需要优化。它的工程含义不是"别优化"，而是：

    在测量出"哪里慢、慢多少"之前，任何优化都是在猜。

    凭直觉优化，最常见的结果是：花了大力气优化了一个根本不在关键路径上的代码，整体性能毫无变化，还引入了复杂度。正确顺序永远是 测量 → 定位热点 → 优化热点 → 再测量验证。

    1.2 四类瓶颈¶

    性能问题归因后，无非四类：

    瓶颈 特征 对策
    CPU 计算密集、纯 Python 循环慢 换算法、缓存、C 扩展、多进程、向量化
    Memory 内存暴涨、频繁 GC 生成器流式、__slots__、减少拷贝
    IO 等待磁盘/网络，CPU 空闲 异步、并发、批量
    Network 网络往返多、延迟高 连接复用、并发请求、就近部署

    先分清瓶颈是 CPU 还是 IO，是性能优化的第一性判断——IO 密集用 asyncio（第四章已讲），CPU 密集用多进程/向量化，两者手段完全不同，用错方向等于白干。

    二、性能分析工具¶

    2.1 timeit：微基准¶

    测一小段代码的执行时间，用标准库 timeit：

    import timeit

t = timeit.timeit("'-'.join(str(n) for n in range(100))", number=10000)
print(t)   # 跑 10000 次的累计秒数

    timeit 会自动跑多次、取稳定值，避免单次测量的抖动。命令行也能用：python -m timeit "x = sum(range(1000))"。

    2.2 cProfile：定位热点¶

    微基准只能测已知的片段；想知道"整个程序里到底哪里慢"，用 cProfile——它记录每个函数的调用次数和耗时，帮你定位热点（hotspot）：

    import cProfile, pstats

pr = cProfile.Profile()
pr.enable()
main()                      # 跑你要分析的代码
pr.disable()
pstats.Stats(pr).sort_stats("cumulative").print_stats(10)

    输出按累计耗时（cumulative time）排序，排在最前面的就是热点。实测示例——slow_loop 里一个 20 万次的循环吃掉了几乎全部时间，fast_path 几乎不耗时：

    ncalls  tottime  cumtime  filename:lineno(function)
     1    0.005    0.005   perf_verify.py:55(slow_loop)   ← 热点
     1    0.000    0.000   perf_verify.py:61(fast_path)

    优化的目标，永远是 cProfile 报告里最耗时的那个函数，而不是你"觉得慢"的那个。

    2.3 memory_profiler / line_profiler（可选）¶

    • line_profiler：逐行分析，精确定位到"哪一行"耗时（需 @profile 装饰器 + kernprof 命令）。
    • memory_profiler：逐行分析内存占用，定位内存泄漏和内存峰值。

    两者都是第三方工具（pip install），在需要逐行精确定位时比 cProfile 更细，但日常先用 cProfile 就够了。

    三、优化手段¶

    3.1 functools.cache / lru_cache：缓存重复计算¶

    如果函数会被用相同参数反复调用，且计算昂贵、结果确定（纯函数），用 functools.cache 缓存结果，把重复计算变成查表。最经典的例子是斐波那契递归——无缓存是 O(2ⁿ) 指数爆炸，有缓存变成 O(n)：

    import functools

def fib_naive(n):                 # 无缓存：指数级
    if n < 2:
        return n
    return fib_naive(n-1) + fib_naive(n-2)

@functools.cache                   # 有缓存：线性
def fib_cached(n):
    if n < 2:
        return n
    return fib_cached(n-1) + fib_cached(n-2)

    实测：fib(30) 无缓存 0.0565 秒，有缓存 0.000004 秒，加速约 1.5 万倍。用 cache_info() 能看到命中统计（hits=28, misses=31），验证缓存在起作用。

    lru_cache 是 cache 的"限量版"，用 maxsize 限制缓存条目数，超出按 LRU（最近最少使用）淘汰，适合"结果集太大、不能无限缓存"的场景。两者都要求参数可哈希（列表等不可哈希参数不能直接用）。

    3.2 asyncio：IO 密集¶

    等待磁盘、网络时 CPU 是空闲的，asyncio 用"协作式单线程"把这些空闲等待填满（第四章已详述）。IO 密集任务从"顺序等"改成"并发等"，吞吐能提升数倍到数十倍，且单线程能扛上万个连接。

    3.3 multiprocessing：CPU 密集¶

    CPU 密集任务受 GIL（全局解释器锁）限制，多线程无法真正并行计算。要榨干多核 CPU，用多进程绕过 GIL：

    from multiprocessing import Pool

def square(x):
    return x * x

with Pool(4) as p:              # 4 个进程并行
    results = p.map(square, range(1_000_000))

    多进程有进程创建和跨进程通信的开销，适合"任务量大、每个任务够重"的场景；任务太轻时开销反而会吃掉收益。

    3.4 vectorization：NumPy 思想¶

    纯 Python 循环慢，是因为每条语句都有解释器开销。向量化（vectorization）的思想是：把"循环里逐元素操作"换成"对整个数组的一次批量操作"，让底层 C 代码替你循环：

    # 慢：纯 Python 循环
result = [x * x for x in range(1_000_000)]

# 快：NumPy 向量化，C 底层批量运算
import numpy as np
result = np.arange(1_000_000) ** 2

    向量化能把数值计算加速一到两个数量级。即使不引入 NumPy，这个思想本身也值得记住：能一次批量做的，别在 Python 层逐元素循环。

    四、必做项目：性能提升 ≥ 3 倍¶

    完整示例代码项目待补，可直接用一个已有的、有性能问题的函数练手。

    4.1 需求¶

    选一个已有的、可测出性能瓶颈的项目/函数，优化到性能提升 ≥ 3 倍，并输出 Profiling 报告与优化分析文档。

    4.2 方法论（务必按顺序）¶

    1. 建立基线：用 timeit 或 perf_counter 测出当前耗时，记为基线。
    2. 定位热点：用 cProfile 找出最耗时的函数/代码段。
    3. 判断瓶颈类型：是 CPU、Memory、还是 IO？这决定优化方向。
    4. 选手段：CPU → 换算法/缓存/向量化/多进程；IO → asyncio/并发；Memory → 生成器/减少拷贝。
    5. 优化 + 复测：改一处、测一次，确认真的变快（而不是"感觉快了"）。
    6. 写报告：记录"基线 → 瓶颈定位 → 手段 → 结果"的完整链路。

    4.3 验收标准（毕业标准）¶

    1. 性能提升 ≥ 3 倍：同一输入、同一环境，优化后耗时 ≤ 基线的 1/3。
    2. 有 Profiling 报告：cProfile 输出证明"确实定位到了热点"。
    3. 有优化分析文档：写清瓶颈类型（CPU/Memory/IO）、采用的手段、为什么有效。
    4. 结果正确：优化后结果与优化前完全一致（性能优化不能以牺牲正确性为代价）。
    5. 手段恰当：IO 密集用了异步、CPU 密集用了多进程/缓存/向量化，而非"为了用而用"。

    五、全章速查表¶

    知识点 一句话要点

    过早优化 Knuth：约 97% 的时候不需要优化，先测再优化
    四类瓶颈 CPU / Memory / IO / Network，先分清再选手段
    timeit 微基准，自动多次取稳定值
    cProfile 定位热点，按累计耗时排序
    line_profiler 逐行精确定位（第三方）
    memory_profiler 逐行内存分析（第三方）
    functools.cache 缓存重复计算，fib(30) 加速约 1.5 万倍
    lru_cache 限量缓存，maxsize + LRU 淘汰

    六、贯穿全章的一条判断¶

    最后收束到这一章要建立的认知：

    性能优化的核心能力，不是背一堆技巧，而是"先测出热点、再对瓶颈下药、最后用数据验证"这套纪律。

    • 想要知道哪里慢 → cProfile 定位热点，别靠直觉。
    • 想要CPU 密集变快 → 缓存重复计算、向量化、多进程。
    • 想要IO 密集变快 → asyncio 并发（第四章）。
    • 想要内存不爆 → 生成器流式（第七章）。

    理解性能的标志，不是会背 cache 的用法，而是能说清楚：为什么要先测量、CPU 和 IO 密集各该用什么手段、怎么验证优化真的生效。这套"测量-定位-优化-复测"的纪律，比任何单个技巧都值钱——因为技巧会过时，纪律不会。
